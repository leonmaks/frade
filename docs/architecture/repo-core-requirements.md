# Frade Repo Core — нормативные требования

Статус: целевые требования, 2026-09-24. Завершение подтверждается только исполненными проверками в `openspec/changes/frade-repo-core/evidence/acceptance.md`.

## Требования и критерии приёмки

| ID       | Требование                        | Критерий приёмки                                                                |
| -------- | --------------------------------- | ------------------------------------------------------------------------------- |
| CORE-001 | Независимость доменной модели     | Domain не импортирует инфраструктуру, UI и runtime                              |
| CORE-002 | Конфигурируемая метамодель        | Новый тип добавляется конфигурацией без изменения Core                          |
| CORE-003 | Стабильная идентичность           | Переименование и перенос файла не изменяют ID                                   |

## Обязательные ADR

- ADR-001 Source of Truth: файлы — источник истины файлового адаптера; SQLite — производный индекс. Для PostgreSQL источником истины является БД.
- ADR-002 Stable Identity: ID не зависит от имени, пути, позиции или порядка загрузки. Источник без устойчивых ключей требует явного identity mapping.
- ADR-003 Metamodel Ownership: метамодель принадлежит профилю; Core интерпретирует и валидирует её без корпоративного перечня типов.
- ADR-004 Change Boundary: все доменные мутации проходят через Command Service; независимые репозитории не образуют одну атомарную транзакцию.
- ADR-005 Diagram Independence: диаграмма — отдельный документ с экземплярами элементов и необязательными привязками. Core не владеет координатами и маршрутами.
- ADR-006 Explicit Capabilities: адаптер объявляет только реализованные, проверенные возможности; отсутствие возможности обнаруживается программно.
- ADR-007 No Silent Data Loss: неподдерживаемое преобразование или конфликт запрещает перезапись; ошибка содержит безопасные сведения для восстановления.

## Конечный автомат сессии

- `CLOSED → OPENING → READY | READ_ONLY | DEGRADED | ERROR`.
- `READY | READ_ONLY → DEGRADED | CLOSING`; `DEGRADED → READY | READ_ONLY | ERROR | CLOSING` после явной повторной проверки.
- `ERROR → OPENING | CLOSING`; `CLOSING → CLOSED`.
- В `OPENING` изменения недоступны. В `READ_ONLY` разрешены запросы, запись отклоняется.
- В `DEGRADED` возможности определяются исправностью источника; неизвестная целостность запрещает запись.
- `ERROR` не выдаёт частично открытую сессию за рабочую.
- `CLOSING` отвергает новые операции и завершает либо отменяет активные по документированной политике.
- В `CLOSED` освобождены ресурсы, подписки, watchers и соединения.

## Консистентность записи

Однофайловая запись: подготовить содержимое, проверить исходную ревизию, записать временный файл в том же каталоге, синхронизировать и атомарно заменить там, где это поддерживает ФС. Проверять ревизию непосредственно перед заменой. Защита от межпроцессных гонок требует дополнительной координации; одно сравнение хеша не является compare-and-swap файловой системы.

Многофайловая запись: не объявлять полную атомарность без соответствующего механизма. Нужны staged write и журнал восстановления либо явная политика частичного результата. `SUCCESS` недопустим после частичного применения. Прерванная запись обнаруживается при открытии; пользовательские данные не удаляются молча.

Ошибка индекса после подтверждённой записи не отменяет изменение. Индекс переходит в `OUT_OF_SYNC` и восстанавливается; команда не применяется повторно ради индекса.

Ошибка доставки события после записи не откатывает источник. Подписчикам доступен resync. Долговечная доставка требует реализованного журнала/outbox, а не только интерфейса.

## Объём и контроль завершения

P0: канонические контракты, профили/сессии, существующая конфигурируемая метамодель, ссылки, валидация, порты, native YAML/JSON, ограниченные запросы графа, CRUD, конфликты и события.

P1: производный SQLite, внешние изменения, диагностика, отдельный Git provider, Desktop/Web transport, bridge и автономные диаграммы.

P2: проверяемые PostgreSQL/remote/federation/search контракты и batch import/export; PostgreSQL implementation только при наличии локальной тестовой БД и миграционной инфраструктуры. Неизвестная внешняя схема не выдумывается.

Последовательность: G0 discovery → G1 SDD/ADR → G2 BDD/traceability → G3 domain → G4 storage → G5 application → G6 integration → G7 regression → G8 evidence → G9 archive. Неуспешный gate запрещает продвижение зависимого этапа и архивацию.

Проектные размеры benchmark fixtures: Small 1 000/3 000 объектов/связей; Medium 100 000/300 000; Large 1 000 000/3 000 000. Измерять cold open, index build, ID lookup, filter, incoming edges, bounded traversal, update, incremental index и память. Бюджеты устанавливаются после baseline на доступном оборудовании. Корректность записи и восстановления обязательна независимо от скорости.
