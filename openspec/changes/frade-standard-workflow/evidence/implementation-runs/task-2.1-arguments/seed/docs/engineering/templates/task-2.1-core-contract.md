# Direction core contract v2

This is the installable data and guard contract for task 2.1. It is a library, not a command dispatcher or a gate receipt. The planning draft manifest contains explanatory scope strings; an installed manifest uses only canonical repository paths and explicit closure fields as shown in `direction-manifest.v2.json`. The example's zero hashes and baseline are synthetic and grant no authority.

## API and data

`scripts/directions/contracts.mjs` exports `validateManifest(manifest)`, `scopeFingerprint(manifest)`, `validateTraceability(trace, options)`, `verifyTraceability(trace, {boundary,snapshot})`, `validateApplicability(plan)`, `verifyApplicability(plan, {boundary,snapshot})`, `safeId`, `safeRepoPath`, `safeOwnerPath`, `pathMatches`, and the exact phase, health, applicability enums. Validators return `{ok, issues}` with stable `{code,path,detail}` entries. Structural `ok` does not prove that Git ownership, a run, a review, or a human decision happened. The two asynchronous verify functions require current raw run evidence through the trusted boundary. Version 2 is the only accepted manifest version. Unknown versions fail closed.

Direction IDs and stage IDs are stable. Owner branch is `codex/<id>` and the Windows worktree/common paths are canonical absolute paths. Repository paths use `/`, no traversal, link escape, alternate data stream, control character, `.git` segment, device name or uncontrolled wildcard. Real Git registration, case collisions and reparse points must also be checked by the future bootstrap or executor before a write. The manifest has distinct `scope.planningAllowed`, `scope.allowed`, `scope.frozen` and `scope.closure`; closure paths never enter routine `allowed`. W01's three exact spec destinations and owner-bound archive pattern are fixed by design. The archive date is a real canonical UTC `YYYY-MM-DD` chosen at execution.

`scopeFingerprint` hashes only semantic scope: owner, baseline, policy, path sets, closure destinations, stage dependencies, role authority and task acceptance links. Phase, health, checkbox completion, admission display strings, checkpoint and metrics are progress fields. They do not change this fingerprint. Any semantic change requires coherent revalidation and a new approval/review binding. The raw approved plan SHA256 remains separate. PRE binds the reviewed plan and scope fingerprint; approved implementation source changes do not stale PRE. GREEN, checks, Verify and POST bind the current source and config hashes. POST also binds plan and scope.

The trace contract has `requirements`, `scenarios`, `tasks`, `assertions` and `runs` arrays. Stable requirement IDs link to scenarios, reciprocal task links, assertion IDs and run IDs. Critical requirements require positive, negative and boundary controls. A scenario classified `human` or `future` needs a concrete `boundaryReason`; it is never executable acceptance. Unresolved acceptance blocks dependent implementation while research can continue. Run rows require source/config SHA256 and environment and retain FAIL/BLOCKED records. `verifyTraceability` checks current referenced PASS runs against trusted raw proof; older unreferenced FAIL rows remain in the history. Approved numeric limits remain in the owning contract and must not be changed to match a failure.

The applicability contract has `checks` with `REQUIRED` or `NOT_APPLICABLE`, affected contracts and previous results. An affected or currently failing check cannot become N/A, and N/A needs a concrete contract reason. A required NOT_RUN/FAIL/BLOCKED check stays nonpassing. `verifyApplicability` requires trusted current proof for each required PASS. The verifier supplying check proof must compare the declared plan with actual commands, config, source, environment and raw run output. Scoped AGENTS and subsystem rules remain mandatory; this library cannot semantically waive them.

## Evidence boundary

`scripts/directions/evidence.mjs` exports `createArtifactReader(root)`, `verifyArtifactHash(reader, descriptor)` and `createEvidenceBoundary({verify})`. The reader checks relative paths, symlinks and canonical containment and returns raw bytes and SHA256. The trusted `verify` callback is an integration boundary, not a JSON parser: it must read and hash actual artifacts, compare source/config/run bindings, and for independent reviews check complete raw events, exit, report, candidate/packet/control/plan hashes, one unambiguous verdict, scope and currentness using the verified transport receipt. It must verify human policy decisions and owner checkpoints from their own authority. The caller must not construct a verifier that returns true from a manifest `PASS`, a boolean, or request metadata. No verifier is supplied by default. The later review wrapper and Git controls own those checks; this task does not claim they exist.

A gate reference contains `kind`, `status: "PASS"`, `scope: "full"`, `complete: true`, `artifact: {path,sha256}` and `bindings`. These fields are necessary descriptors and never sufficient approval. `evaluateTransition` additionally requires a genuine boundary created with `createEvidenceBoundary`; a copied JSON object or object with a `verify` method is not one. A trusted callback may return true only after its raw proof checks. Missing, stale, malformed, focused or unverified proof returns a specific `*_PROOF` issue. Actual backend/effort remains `NOT_CONFIRMED` without separate attestation.

`scripts/directions/lifecycle.mjs` exports `evaluateTransition({manifest,stageId,target,evidence,boundary,snapshot})` and conservative `legacyClosureState(record)`. Only the next phase is admissible. A FAIL/BLOCKED/PAUSED owner stops. `snapshot` supplies current plan, scope, source and config SHA256. PRE plus policy decision and owner checkpoint are required before BDD/TDD and implementation; RED before implementation; current GREEN/checks/Verify before POST; current independent POST before archive. A diagnostic PASS never replaces full approval. `legacyClosureState` maps completed old checkboxes to `IMPLEMENTED_PENDING_CLOSURE` even if historical text says PASS; only an actual verified closure operation may establish CLOSED.

`scripts/directions/scope.mjs` exports `checkScope(manifest,phase,paths)`, `planClosure(args)` and the bounded `executeClosure(args)`. `checkScope` checks planning or implementation relative paths against frozen and allowed sets and always rejects closure paths. `planClosure` is a read-only proposed operation list after verified archive barriers. It requires exactly the declared delta spec syncs, one move of the selected owning active change to the exact dated archive, and explicit owned/immutable-origin mappings with raw hashes. Each relocated path retains its suffix under the archive root. With `reader: createArtifactReader(root)`, it also verifies each delta source's `sourceSha256` and each reference origin's SHA256 against actual bytes. Without a reader, a successful plan validates only path structure and gate references and is not ready for filesystem mutation. `executeClosure` performs the further Git and filesystem checks described below before writing only in disposable test repositories. This task does not perform W01 sync or archive.

## Stable issue groups

Schema/identity: `SCHEMA_VERSION`, `DIRECTION_ID`, `OWNER_BRANCH`, `OWNER_PATH`, `UNSAFE_PATH`, `FROZEN_OVERLAP`. Scope/closure: `SCOPE_DENIED`, `CLOSURE_INACTIVE`, `CLOSURE_DESTINATION`, `ARCHIVE_DATE`, `ARCHIVE_DESTINATION`, `REFERENCE_RELOCATION`. Lifecycle/evidence: `PHASE_ORDER`, `HEALTH_STOP`, `SCOPE_DRIFT`, `EVIDENCE_BOUNDARY`, `PRE_PROOF`, `GREEN_PROOF`, `VERIFY_PROOF`, `POST_PROOF`. Trace/applicability: `UNRESOLVED_ACCEPTANCE`, `TRACE_TASK`, `TRACE_ASSERTION`, `TRACE_RUN`, `CONTROL_NEGATIVE`, `CONTROL_BOUNDARY`, `FALSE_NOT_APPLICABLE`, `REQUIRED_CHECK_NOT_PASS`. Other issue codes follow the same `{code,path,detail}` shape.

## Task 2.1 repair and schema migration

Version 2 remains the manifest schema. Its `stages[].change` is an explicit, safe, unique mapping to an OpenSpec change within `scope.planningAllowed`; the direction ID continues to identify the branch. A multi-stage direction can therefore own independent numbered changes. `scope.closure.archiveOwner` selects an owned stage change for one bounded closure. W01 keeps its three exact capability spec destinations. Other directions may declare only `openspec/specs/<safe-capability>/spec.md`, never a product or frozen path. Paths reject Windows-invalid characters and case-fold conservatively for scope and frozen checks. Generic stable requirement IDs such as `DRAW-CORE-12` are accepted alongside `FWE-004`.

The `evaluateTransition` API now checks `stage.failedFixes` for two deterministic FAIL outcomes of one defect. Another implementation transition requires `stage.rca` with one root AGENTS classification, concrete root and layer, and current trusted `evidence.rca` proof. `CLOSED` requires the actual closure receipt plus trusted `evidence.archive` proof bound to the operation digest, owner, current source/scope and archive HEAD. A PASS string or raw JSON boolean cannot supply either proof. `createEvidenceBoundary` remains an explicitly trusted integration adapter; task 2.5 owns actual review-protocol verification.

`scope.mjs` also exports `executeClosure(args)` and `isClosureReceipt`. The executor is deliberately limited to isolated temporary Git roots named `frade-closure-*`, with no remote, a clean tree, exact owning branch, current HEAD and ancestor original baseline. It rechecks gate proofs, declared operations, all owner files and raw hashes, destination contents, links, case collisions and symlink safety before writes. It merges only exact delta requirement sections into exact capability spec files, preserves unrelated requirements, moves only the owning change, relocates owned relative links and role-source paths through an explicit origin map, and preserves immutable raw files and origin hashes. The actual W01 archive still belongs to its later Verify/POST/closure sequence. The original tests-only historical RED snapshot remains distinct from the later controlled behaviorless skeleton replay under `deliverables/repair-red`.
