# Design — Common Frade workflow

## Context

The v3 transport in evidence/transport-v3-origin is proven by15 adversarial tests, a real root-deny probe and completed UI PREs. It hardcodes UI candidate/branch/process-root/authority. Windows native sandbox could not provide equivalent root denial; the existing WSL Ubuntu-22.04_E/public Codex0.159.3 runtime did. All current Frade worktrees share E:/dev/codex/frade/.git. Routing's dirty/frozen ownership and failed applicable gates remain its owner responsibility.

## Goals / Non-Goals

One current-host review service/policy for every registered Frade worktree, automatic independent reviewer result reception and honest branch progress. Preserve phases/STOP, user data, immutable evidence and domain contracts. No product code, account-global config, credentials copy, automatic downgrade, force Git, CI-protection claim, concurrent active-checkout writer, routing gate bypass or P01 popup acceptance.

## Decisions

### Shared delivery and discovery

Repository source scripts/agent-review contains a small generic front-end plus exact v3 transport templates/probe under transport/. Front-end resolves current working Git root/common directory with Git, checks it against the installed release's original Frade common directory and registered worktree inventory, and rejects an unrelated repository even with the same origin URL. Never accepts an arbitrary source worktree from request. Review storage is shared common-dir/frade-workflow/runs/<unique-run>; each run has isolated request/prompt/instance/prepared/output, no cross-run global mutable files. There is no per-branch model/provider config.

A release in common-dir/frade-workflow/releases/<content-hash> contains only reviewed public policy/docs/runner/templates/probe and exact hashes, plus original common-dir binding. Atomic current.json points to the release; no Git hooks/global settings. Front-end run from any worktree derives its owning root/branch automatically. Shared publication is content/version based, not full UI-branch merge. Existing active Routing files stay unchanged; the owner loads central policy and adopts any required tracked process/control records in its own reviewed scope. Root UI AGENTS gets additive section20. The passive primary AGENTS receives only the same additive loader/summary with exact before/after byte preservation after review; active Routing AGENTS is not edited here. An already-running stale conversation cannot be silently reinstructed: explicit provided Routing handoff loads the shared release once. No additional branch/account setup is needed thereafter. Other Git branches acquire root rules when process commit is adopted; central executable remains available regardless of branch ancestry. Do not claim all old branch instruction files are rewritten.

### Reuse proven confinement

Front-end takes an agent-authored external JSON with phase PRE/POST, selected source-relative paths, scope, active change and full prepared review prompt. Requests are task inputs, not user configuration. Generate an isolated instance of immutable reviewed v3 templates with narrowly checked replacements: candidate=current registered root, process-root=this run, authority=shared Frade policy; prepare branch guard=current selected branch instead of fixed UI name; replace the UI-only manifest selection statement and recorded authority with actual shared policy adoption paths. Use JSON literals, require exactly one match for each replacement and hash-bind both original templates and generated instance. Other inherited transport logic stays byte-equivalent, including pinned public runtime, root deny/minimal tools/packet-only reads, no network/apps/writes and fixed clean environment. The generated instance adds exactly-once audited instruction-isolation controls: project_doc_max_bytes=0 and project_doc_fallback_filenames=[] configs and --ignore-rules alongside --ignore-user-config. Thus automatic global/project AGENTS content and exec-policy rules do not enter reviewer context; relevant AGENTS files are explicitly selected packet artifacts. Verify public CLI support and actual generated configs with fresh contextual probes. No auth/global configuration is selected in the packet. Authenticated harness outside sandbox uses existing signed-in account; --ignore-user-config remains. Do not copy its auth into the instance.

Runtime0.159.3 and actual probe configs must match; a missing runtime/probe, altered template/config, unsupported sandbox or CLI failure is BLOCKED. Add a fresh contextual probe from both UI and Routing worktrees against the same policy: allowed packet read, candidate/common-dir/other-worktree/auth/config denied, write/socket denied. This is read-only with respect to feature checkout; probe fixtures live in common run storage. Requests/instance/probe/results stay outside candidate.

Wrapper preserves v3 full tracked+nonignored-untracked candidate identity/bytes and raw selected file provenance. All selected files pass current path/secret guard. Index must be empty; HEAD/branch/status/source/packet/request/prompt/toolchain must be unchanged through review. Missing necessary packet input is a review blocker; never send the whole repo just to avoid selecting inputs. Exclude Git/auth/secrets/global settings and other repositories. To preserve inherited v3 source-copy guarantees, an old-branch owner saves the reviewed shared policy/authority and needed public release control artifacts with exact version/origin/hashes into its approved process evidence directory before freeze, selects those paths in the packet, and records adoption. The front-end requires that policy artifact in request paths; it does not auto-write the feature checkout. No foreign uncommitted product data is transferred. This one-time owner adoption is a control/evidence task, not per-branch model/account configuration or a UI completion dependency.

### Independent gate semantics

Request gpt-6-astra/xhigh in a fresh ephemeral external CLI invocation, no author context or writable candidate; keep requested vs actual backend/effort separate. No substitution without explicit decision. PRE after approved coherent plan/validation before production; POST after implementation/required checks/OpenSpec verification before archive. The generic outer wrapper independently validates raw CLI outputs before issuing an authoritative receipt, regardless of inner v3 status. Automated reception needs clean exit0, valid JSONL event order with a started thread, no failed/error events, every started turn completed and final event turn.completed, exactly one verdict matching the whole single line ^[ \t]*GATE_STATUS:[ \t]*(PASS|FAIL)[ \t]*$ (optional literal escaped underscores normalized), all integrity proofs. Reject split-line verdicts and a completed turn followed by an incomplete started turn. Real Codex exec streams may have no turn.started: require a nonempty thread, exactly one final turn.completed with no subsequent events when no turn.started is emitted. Add RED/GREEN for both defects and actual valid stream. Inner v3 receipt is retained as raw historical evidence; only strict outer receipt may authorize progression. Invalid/missing/mutated/timed-out result is BLOCKED. Preserve raw failure outputs. FAIL stops that scope; independently applicable failed tests cannot be waived by review. Focused PASS does not certify cumulative product closure or human visual baseline. Existing stricter owner gates and numbered STOP remain. Machine gate alone is not independent approval. Human only resolves actual scope/spec/permission/visual decisions or unresolvable environmental authorization; no review prompt relay.

### Progress policy

Every engineering branch owns a tracked *-STATUS.md with branch/worktree, active change/origin/checkpoint, phase/task list, actual test/gate state, blockers/decisions, next step, commits/push and UTC evidence/MSK display. Existing UI/Routing program dashboards are retained; otherwise docs/engineering/BRANCH-STATUS.md is the default. Status is written by its owning agent on start/resume and meaningful events, never during frozen review. Scope/contract/task files are authority; dashboard is a current projection, not approval. Open in right panel with actual queued/visible outcome. Preserve dated evidence, don't rewrite old FAIL. Shared policy carries no shared feature-progress file. Checkpoint commit/push follows user destination authorization, owner-specific scope and no-force safety; a FAIL checkpoint is explicitly incomplete, not advancement.

### Deployment and self-review

User request is explicit broad Frade authorization, saved verbatim. Supplier process artifacts have their own PRE/meaningful RED/GREEN/verify/independent POST. Initial PRE/POST use the already authorized confined UI transport with the new process-only packet and full v3 originals, avoiding self-approval by newly written code. After POST PASS publish exact release hashes atomically in common-dir and run contextual probes/version discovery from UI and Routing, without editing Routing. Save installation evidence and primary append provenance. Revalidate actual source release hashes after installation. Commit process-only shared files separately from P01 status/evidence; current branch push remains authorized destination. Owner consumption keeps its original baseline/fingerprints and reviews actual shared process adoption; no broad allowlist/baseline move. STOP on supplier failure; no rewrite of Routing historical result.

## Risks / Trade-offs

[Stale branch instruction files] -> canonical shared release plus exact owner handoff; truthful deployment inventory. [Different host runtime] -> one-time environment prerequisite and BLOCKED, no per-branch config or weaker sandbox. [Concurrent features] -> unique run directories and no writes to active foreign checkouts; consumer owns frozen-control adoption. [Template drift] -> pinned provenance/replacement-count/hash tests. [Credential-shaped data] -> packet guard and excluded paths, no blanket suppressions. [Inaccurate model claims] -> requested metadata with NOT_CONFIRMED actual. [Self-review bias] -> separate existing read-only transport and new session.

## Migration Plan

Validate accepted supplier artifacts -> existing transport PRE -> meaningful wrapper tests RED -> bounded reuse/front-end/shared policy and docs -> GREEN, all15 inherited controls and fresh contextual probes -> supplier verify -> existing transport POST -> content-hash release publication and exact passive primary loader append -> install checks/owner Routing handoff -> supplier archive/checkpoint. Original v3/historical UI reviews remain unchanged and callable.
