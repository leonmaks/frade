# Frade UI style guide v1.0

Дата: 30 сентября 2026. Область: все пользовательские интерфейсы Frade — Electron, веб-вариант, Frade Draw, Repository, Projects, AI, Settings. Стек desktop: Electron; Tauri не используется.

Это нормативный стайл-гайд и проект основы дизайн-системы. Он задаёт требования для новых UI-изменений после включения в репозиторий. Документ, токены и визуальный образец подготовлены; существующее приложение не проверялось и не изменялось. React-компоненты, Storybook и CI ещё требуется внедрить в реальный код. Путь `E:\dev\codex\frade` недоступен из этой сессии.

## 1. Выбор основы

**Решение: сохранить модель рабочего пространства VS Code; оформить единую собственную дизайн-систему Frade.** Визуальное направление: личная архитектурная мастерская — глубокий графит, выразительный холст, точный синий акцент, приятный тактильный отклик и ясный рабочий контекст. Fluent 2 служит ориентиром для аккуратности и фокуса; Carbon — для сложных таблиц; Material 3 — для семантических токенов и адаптивных областей. Каждый заимствованный паттерн переводится в правила Frade, без параллельных визуальных систем в одном приложении.

VS Code — продукт и набор workbench-паттернов, а Material, Fluent, Carbon и Spectrum — дизайн-системы. Они сравниваются здесь как возможные основания интерфейса, а не как эквивалентные библиотеки.

### 1.1 Сравнение

Следующая таблица — экспертная оценка соответствия задачам Frade. Это не измерение популярности, красоты или результатов пользовательских тестов.

| Основа | Сильная сторона | Что потребует адаптации для Frade | Решение |
|---|---|---|---|
| VS Code workbench | Дерево, группы редакторов, вкладки, команды, панели, рабочий контекст | Нужны собственные формы, табличные выборы и описание визуальных токенов | Основная структура и поведение |
| Fluent 2 | Фокус, привычность на платформе, согласованные компоненты | Структуру архитектурного редактора всё равно нужно проектировать | Визуальный ориентир |
| Material 3 | Токены, цветовые роли, адаптивные компоновки | Базовые размеры и выразительность нужно подстроить под плотное рабочее пространство | Отдельные принципы; полная смена основы не выбрана |
| Carbon | Таблицы, фильтры, массовые действия, корпоративные данные | Workbench и редактор диаграмм остаются собственными | Табличные паттерны |
| Adobe Spectrum | Согласованность продуктов, токены, интерфейсы профессиональных инструментов | Потребуется адаптация к репозиторию и его редакторам | Дополнительный референс |

У Fluent 2 есть публичные примеры применения в продуктах Microsoft; у Spectrum — в Adobe; у Carbon — в IBM; у Material — собственная экосистема. Это подтверждает наличие зрелых экосистем, но не позволяет честно ранжировать распространённость по числу приложений. Для Frade решающим является соответствие задачам, а не размер экосистемы.

**Визуальный выбор:** выразительная мастерская на базе workbench VS Code. Должна возникать эмоциональная связка «здесь моя работа → здесь я понимаю сложное → здесь у меня получается → сюда приятно вернуться». Это проектная гипотеза, а не доказанное обещание удержания. Проверить её следует на сценариях «найти объект → открыть → изменить → сравнить → сохранить» и «открыть диаграмму → выбрать поток → изменить связь», а также при возвращении после перерыва.

### 1.2 Что дают указанные материалы

Material 3 описывает визуальное проектирование: токены и роли. Google Developer Documentation Style Guide описывает технические тексты; он не задаёт цвета или размеры кнопок. Статья Wrike на Habr посвящена API Style Guide; для UI из неё используется организационный принцип согласованности и разделение обязательных требований и рекомендаций. Её API-рекомендации не переносятся автоматически в архитектуру Frade.

### 1.3 Границы исследования

Официальные руководства VS Code, Fluent, Carbon, Google и W3C изучены по доступным страницам. Главная страница Material 3 требует JavaScript; для Material и Spectrum использованы доступные индексированные фрагменты официальных страниц токенов и цветовых ролей. Полный интерактивный каталог Material не исследован. Репозиторий Frade и текущие экраны не были доступны. Поэтому структура пакетов ниже — целевая рекомендация, а не описание найденной кодовой базы.

## 2. Нормативность и приоритет

**MUST** — обязательное правило. **MUST NOT** — запрет. **SHOULD** — правило по умолчанию; отклонение требует обоснования в UI-решении и ревью. **MAY** — допустимая возможность.

Правила этого документа распространяются на любой новый, изменяемый или генерируемый UI, включая AI-раздел и диалоги. Существующие несоответствия устраняются постепенно, в согласованном объёме изменений. Не требуется переписывать всё приложение ради небольшого UI-исправления.

Нормативный набор: этот документ → `tokens.json` → производный `tokens.css` → контракт общего компонента → визуальный образец. Визуальный образец показывает направление, но не переопределяет текстовые правила.

Утверждённый бренд-пакет Frade остаётся источником логотипа и брендовых активов. Этот документ не переопределяет их геометрию или палитру. Синий акцент интерфейса — предлагаемая UI-роль, не утверждение о цветах бренда. Неизвестные брендовые значения MUST NOT придумывать. Многоцветность логотипа не переносится на рабочие панели.

Ограничения безопасности, доступности и утверждённого change scope обязательны. При конфликте с ранее утверждённой спецификацией Codex MUST зафиксировать конкретное противоречие и подготовить изменение спецификации в установленном workflow; MUST NOT молча переписать контракт. Этот гайд не разрешает менять frozen-файлы и не отменяет последовательные gates Routing V2 или Repo Core.

## 4. Рабочее пространство

### 4.1 Области и размеры

Размеры указаны в CSS px, до пользовательского масштабирования. Таблица задаёт начальные и минимальные размеры, а не фиксированный макет для каждого монитора.

| Область | Правило |
|---|---|
| Title bar | 36; нативные оконные действия Electron; видимые репозиторий/workspace и поиск команд. |
| Activity bar | Ширина 48; ячейка раздела 48 × 48; основные разделы сверху, настройки снизу. |
| Primary sidebar | По умолчанию 280; минимум 200; максимум 480 или 40% ширины окна, меньшее значение. |
| Secondary sidebar | По умолчанию 320; минимум 240; скрываемая. |
| Editor group | Минимум 320 для diagram/editor; форма должна адаптироваться и ниже, если доступная ширина требует. |
| Editor tabs | Высота 36; имена 120–220; при переполнении прокрутка и список открытых редакторов. |
| Toolbar / breadcrumbs | 36 / 28; один уровень toolbar для основной задачи. |
| Bottom panel | По умолчанию 220; минимум 120; максимум 50% высоты; скрываемая. |
| Status bar | 28; короткие состояния и действия; текст не мельче 12. |
| Разделитель | Видимая линия 1; hit area 8; курсор resize; клавиатурное изменение через фокус и стрелки. |

Значения относятся к одному горизонтальному слою и применяются только когда хватает места. Нельзя поддерживать все минимумы за счёт сжатия редактора до нерабочей ширины.

### 4.2 Переключение разделов

Activity bar выбирает **раздел приложения**: Repository, Draw, Projects, AI, Search, Source Control. Названия локализуются; набор определяется реально доступными возможностями. Раздел открывает свой навигатор и восстанавливает последнюю активную вкладку/группу, позицию прокрутки и выделение. Несохранённые редакторы сохраняются в workbench; уход в AI не означает их закрытие. Повторное нажатие активной иконки MAY скрывать/показывать sidebar, если это единообразно во всех разделах.

Крупные кнопки «ИИ», второй activity bar, отдельная верхняя навигация и собственная тема AI MUST NOT появляться внутри рабочего пространства. Для AI используется та же вкладочная модель и панель управления, что для остальных разделов.

### 4.3 Адаптация

| Ширина окна | Поведение по умолчанию |
|---|---|
| ≥1440 | Доступны обе sidebar и несколько editor groups при соблюдении минимумов. |
| 1100–1439 | Secondary sidebar скрыта по умолчанию; пользователь может открыть её. |
| 800–1099 | Одна видимая editor group; остальные сохраняются и доступны переключением; sidebar скрываемая. |
| <800 | Навигатор открывается как временная область поверх содержимого; форма и чат переходят в одну колонку. |

Desktop SHOULD поддерживать минимальное окно 800 × 600. Web MUST адаптироваться ниже этой ширины. При увеличении масштаба применяется фактическая CSS-ширина, а не размер экрана. Панели, скрытые из-за недостатка места, восстанавливаются при расширении; пользовательский выбор сохраняется отдельно. Смена размера не теряет вкладки и не меняет данные.

Холст диаграммы MAY сохранять двумерную навигацию и прокрутку. Окружающие формы, инструкции, диалоги и панели MUST адаптироваться при 200% увеличении и до эффективной ширины 320 CSS px там, где критерий reflow применим. Для 2D-содержимого исключение не распространяется на весь интерфейс.

## 5. Визуальная основа

### 5.1 Токены и темы

`tokens.json` — единственный редактируемый источник значений в пакете. `tokens.css` генерируется скриптом. Это простой формат Frade v1, не заявленный стандарт DTCG. Компоненты используют роли `surface.*`, `text.*`, `border.*`, `action.*`, `selection.*`, `focus.*`, `status.*`, `diagram.*`, а не конкретный оттенок.

| Роль | Light | Dark |
|---|---|---|
| Рабочая поверхность `surface.base` | #FFFFFF | #181A1F |
| Панели `surface.panel` | #F5F6F8 | #202329 |
| Activity bar `surface.rail` | #EAEDF1 | #15171B |
| Основной текст `text.primary` | #20242B | #E6E9EF |
| Вторичный текст `text.secondary` | #535D6A | #AAB3C2 |
| Основное действие `action.primary` | #245FC7 | #89B4FF |
| Текст на основном действии | #FFFFFF | #111827 |
| Focus ring | #245FC7 | #89B4FF |
| Выделение `selection.bg` | #E3EDFF | #283D5E |
| Ошибка `status.error` | #B42318 | #FFB4AB |

Цвет ошибки не означает удаление объекта из репозитория. Статус объекта и состояние UI имеют разные токены. Значения полного набора и варианты high contrast находятся в JSON.

Темы: пользователь выбирает light / dark / high-contrast / system. В system приложение наблюдает изменения системной темы; явный выбор имеет приоритет. В `forced-colors` применяются системные цвета, включая SVG и подписи холста. Canvas-рендерер MUST получать отдельный доступный mapping и альтернативное представление; CSS-переменных для DOM недостаточно. Пользовательский override MAY задавать роли только после проверки контраста.

**Light и dark входят в одну поставку.** Реализация одной темы с обещанием второй позже не проходит UI gate. В Settings MUST быть переключатель «Светлая / Тёмная / Как в системе» и доступ к высокому контрасту. По умолчанию — «Как в системе»; пользовательский выбор сохраняется. Переключение применяется ко всему workbench без перезапуска и вспышки неверной темы при запуске. Скриншоты изменённого экрана и контраст его состояний проверяются отдельно в light и dark. Красивую тёмную тему нельзя получить ценой менее качественной светлой.

MUST NOT добавлять HEX/RGB/HSL в feature-компоненты, вычислять тему через opacity белого/чёрного, дублировать палитру в Draw и AI или включать автоматическую смену акцента по обоям. Прозрачные состояния MAY использоваться только как общий проверенный токен с известным фоном.

### 5.2 Типографика

| Назначение | Размер / line-height | Weight |
|---|---|---|
| Основной UI compact | 13 / 20 | 400 |
| Основной UI comfortable | 14 / 22 | 400 |
| Подпись, статус, метаданные | 12 / 18 | 400 |
| Название панели / секции | 13 / 20 | 600 |
| Заголовок редактора | 18 / 26 | 600 |
| Заголовок диалога | 20 / 28 | 600 |
| Текст чата / длинное описание | 15 / 24 | 400 |
| Код / ID / путь | 13 / 20 monospace | 400 |

UI font: `Segoe UI`, затем системные sans-serif с поддержкой кириллицы. Code font: `Cascadia Code`, `Consolas`, затем системные monospace. Без сетевой загрузки шрифтов по умолчанию. Имена объектов и разделов не выводятся целиком monospace. Заголовки — sentence case, не ALL CAPS. Размеры задаются в rem и учитывают увеличение шрифта. Стабильная высота строки является минимумом: текст с пользовательским размером не обрезается.

### 5.3 Плотность, геометрия и движение

| Параметр | Compact (desktop по умолчанию) | Comfortable |
|---|---|---|
| Строка дерева / одноэтажной таблицы | минимум 28 | минимум 36 |
| Control / button | минимум 28 | минимум 36 |
| Промежуток label → field | 4 | 4 |
| Промежуток полей | 12 | 16 |
| Внутренние отступы панели | 12 | 16 |
| Минимальная сенсорная цель | 44 × 44 при coarse pointer | 44 × 44 при coarse pointer |

Шкала отступов: 2, 4, 8, 12, 16, 24, 32, 48. Отступ 2 — для внутренней оптической коррекции, не для компоновки формы. Радиусы: 0 для оболочки и таблиц; 4 для полей и кнопок; 8 для меню/диалогов. Pill-форма используется для компактных тегов, не для всех кнопок. Обводка 1; focus ring 2 + offset 2. Тени — только плавающие меню, popover и modal; постоянные панели отделяются поверхностью и разделителем.

Только изменения opacity/color и небольшое раскрытие MAY анимироваться: 120 ms для feedback, 180 ms для overlay; reduced-motion отключает необязательное движение. Перемещение узлов/маршрутов не сглаживается так, чтобы геометрия отставала от указателя. MUST NOT применять blur/glass, градиенты постоянных рабочих панелей, параллакс или крупные декоративные иллюстрации на рабочем холсте. Единственный локальный градиент MAY использоваться в иллюстрации стартовой страницы; текст располагается на сплошной доступной поверхности.

### 5.4 Иконки

Один набор outline-иконок с сеткой 16/20/24. SHOULD использовать уже принятую в репозитории семью, если она соответствует guide; для нового набора предлагаем Codicons как близкий VS Code вариант. Замена семьи — отдельное решение с проверкой лицензии. MUST NOT смешивать Codicons, Fluent, Material и emoji для одного класса действий. Логотип Frade не является иконкой команды. Иконка 16 помещается в цель минимум 24 × 24; activity icon 20 — в 48 × 48. Каждая icon-only команда имеет accessible name и tooltip; tooltip дублирует смысл, но не является единственной подписью для screen reader.

### 5.5 Эмоциональная выразительность: личная мастерская

Frade должен давать чувство владения работой, ясности, профессионального мастерства и заметного результата. Желаемое возвращение возникает через привлекательную среду и понятную следующую задачу. Эти требования дополняют плотный рабочий интерфейс и применяются к реальным действиям пользователя.

| ID | Эмоция | Обязательный дизайн-паттерн |
|---|---|---|
| FDS-011 | «Это моя рабочая среда» | Последний workspace, редакторы и layout восстанавливаются. Стартовая область предлагает продолжить конкретную работу с настоящим именем и состоянием. |
| FDS-012 | «Я управляю сложностью» | Выбор объекта связывает дерево, холст и свойства; подсвечивает релевантное окружение; действие обратимо и предсказуемо. |
| FDS-013 | «Моя работа стала лучше» | Сохранение, проверка и завершение имеют короткий ясный feedback, отражающий фактический результат. |
| FDS-014 | «Здесь красиво работать» | Качественная типографика, согласованные поверхности, ровная геометрия и аккуратный diagram presentation входят в visual gate. |

**Signature moments:** возврат в последний рабочий контекст; подсветка связанного объекта; создание новой связи; успешное сохранение; принятие проверенного diff. Каждому назначается короткий отклик: мягкое изменение цвета/границы за 120 ms, понятная подпись, один смысловой акцент. Движение привязано к действию и не проигрывается по кругу. Сохранение не сопровождается конфетти; подтверждение не заслоняет диаграмму.

**Стартовая область:** один выразительный заголовок «Продолжить работу», последняя диаграмма/проект, недавние документы и полезная команда создания. Миниатюра последней диаграммы MAY показывать настоящее содержимое при соблюдении политики доступа. Для пустого workspace — небольшой архитектурный образец и действие создания. На первом запуске визуальная выразительность выше; при ежедневной работе приложение возвращает пользователя в редактор, если он выбрал восстановление.

**Свет и глубина:** активный редактор — визуальный центр; его поверхность отделена от графитовой оболочки одним тональным шагом. Выбранная фигура получает синий контур и понятную метку привязки. Стандартные невыбранные фигуры нейтральны. Яркость используется на действии и выделении, а не на каждой рамке. Light-тема сохраняет тот же характер через холодные нейтральные поверхности и ту же композицию.

**Результат как награда:** после проверки допустим конкретный итог «Проверено 18 объектов. Ошибок нет», только если это реальный результат. История изменений и сравнение версий делают выполненную работу видимой. Достижения связываются с полезными результатами проекта; счётчики активности и ежедневные серии не нужны для этой версии. Уведомления относятся к рабочему контексту, контролируются пользователем и не давят на возвращение.

**Персонализация:** тема, плотность, расположение панелей, pinned projects, открытые документы и поведение отправки чата. Пользовательские настройки поддерживают комфорт без разрушения общей визуальной системы.

**Проверка эмоциональной гипотезы:** показать рабочий прототип 5–8 представителям целевой аудитории как первый качественный раунд. Дать реальные задачи и возврат после перерыва. Проверить обнаружение следующего действия, восстановление контекста, воспринимаемую красоту/спокойствие/контроль и желание снова использовать. Фиксировать наблюдения и время задач, не объявлять рост retention по оценкам маленькой выборки. Для количественной оценки потребуется отдельный план и реальные данные использования.

## 6. Контракт компонентов

Любой общий компонент MUST описывать anatomy, варианты, размеры, состояния, keyboard contract, accessibility semantics, токены и примеры. Состояния применяются по релевантности: default, hover, focus-visible, active/pressed, selected, disabled, read-only, loading, error. Взаимоисключающие и одновременные состояния задаются явно. Для disabled запрещена активация; фокус зависит от семантики native disabled / aria-disabled. Read-only остаётся читаемым и копируемым.

| Компонент | Правило |
|---|---|
| Button | Один primary на локальную задачу, остальные secondary/quiet. Подпись — глагол и объект. Loading сохраняет ширину и препятствует повторной отправке. |
| TextField / TextArea | Видимый label; placeholder — пример, не label. Required обозначено и объявлено; ошибка связана с полем; введённые данные сохраняются. |
| Select / LoV | Одиночный и множественный выбор визуально различимы. Большие справочники — поиск/таблица, а не огромный dropdown. |
| Menu / context menu | Одинаковые команды и порядок для одинакового объекта. Разделить destructive-действия; keyboard navigation; закрытие Esc. |
| Dialog | Modal только для обязательного решения. Заголовок описывает решение; начальный безопасный фокус; focus trap и возврат; фон inert. |
| Popover | Локальная вспомогательная задача; закрытие Esc/outside; не перекрывает необходимую точку редактирования. |
| Toast | Краткий обратимый результат. Ошибка с потерей данных не исчезает сама. Не заменяет inline-validation. |
| Banner | Состояние всего workspace/редактора: offline, conflict, read-only. Действие исправления рядом. |
| Badge | Короткая метка и смысл через текст/иконку. Цвет не единственный носитель состояния. |
| EmptyState | Что отсутствует, причина при известности, одно полезное действие. Для zero-results — сброс фильтров, а не создание объекта. |
| Progress | Spinner для короткого неизвестного ожидания; progress bar для известной доли; cancel при поддержке операции. |
| Splitter | Размер, минимум, keyboard resize, reset; hover не единственный способ обнаружения. |

Новые компоненты SHOULD сначала реализовываться в общем UI-слое. Допустимо переиспользовать существующие headless primitives для доступного поведения. Выбор Fluent UI/MUI/Carbon React не следует автоматически из визуального выбора: установка нескольких полных библиотек ради отдельных экранов запрещена. Зависимости выбираются после аудита текущего кода и отдельного технического решения.

## 7. Навигатор и вкладки

### 7.1 Дерево репозитория

Иерархия: chevron → иконка типа → имя → компактные признаки изменения/ошибки → контекстные действия. Отступ уровня 16. Длинное имя обрезается визуально с доступным полным именем; путь раскрывается в tooltip/details. Action-иконки MAY появляться на hover, но также на focus-within и через меню клавиатуры. Chevron имеет отдельную hit area. Выделение строки не равно открытию редактора.

Клавиатура следует Tree View APG: ↑/↓ — соседний видимый узел; → — раскрыть/перейти к ребёнку; ← — свернуть/перейти к родителю; Home/End; typeahead; Enter — открыть. Для multi-select используются явные модификаторы и `aria-multiselectable`; выбранность и фокус объявляются раздельно. Виртуализация MUST сохранять корректные aria-level/posinset/setsize и прокручивать focused item в видимость. Нельзя удалять focused item из accessibility tree без перевода фокуса.

Single click на листе открывает preview при включённом preview-mode; double click/Enter «закрепить»/редактирование превращает preview в постоянную вкладку. Preview не заменяет dirty-вкладку. Поведение на родителе не должно неожиданно запускать редактирование: раскрытие через chevron, открытие свойств через Enter/команду, согласно контракту типа.

### 7.2 Editor tabs

Вкладка: иконка типа, имя, dirty marker, close. Один активный tab на группу. Focus и active state различимы. Перемещение tab между группами не меняет идентичность документа. Закрытие dirty-вкладки предлагает «Сохранить», «Не сохранять», «Отмена»; при отказе/ошибке сохранения вкладка остаётся. После закрытия фокус и активность переходят к последней использованной оставшейся вкладке группы; при пустой группе — к её empty state. Это правило задаётся контрактом Frade поверх допустимых вариантов APG.

Tablist: один tab stop; стрелки/Home/End меняют фокус; Enter/Space активируют. Автоматическая активация MAY только при мгновенно доступном содержимом. Переключение Ctrl+Tab — отдельный MRU-путь; Ctrl+W закрывает активный редактор с учётом контекста и platform shortcut registry. Close-button не вкладывается интерактивно в другой button; доступна отдельная команда закрытия и меню. Drag-and-drop имеет команды «Переместить в группу…» и «Разделить редактор».

## 8. Таблицы, LoV и свойства

Таблица объектов MUST поддерживать понятные заголовки, сортировку с направлением, search/filter, настройку столбцов при необходимости, явный selection и контекстные/массовые действия. Numeric — вправо с табличными цифрами; название/описание — влево; дата — локализованно; timezone видима там, где важна. Единицы измерения не смешиваются в столбце без подписи.

Состояния: loading; empty repository; no search results; error; partial data; stale/offline; selection. Сортировка/фильтр/ширины столбцов сохраняются в пределах представления и workspace, не в каждом случайном URL. Отображать выбранное количество и различать «все на странице» / «все результаты». Удаление нескольких объектов показывает состав воздействия до выполнения.

Обычная таблица использует семантику native table. ARIA grid применяется только при реализованной навигации по ячейкам и соответствующем keyboard contract. Нельзя присвоить `role=grid` ради вида. Pagination и virtualization выбираются по данным и проверяются на сохранение selection и keyboard navigation; тестовый крупный dataset — контракт производительности, не случайная магическая граница.

**LoV single:** одна выбранная сущность; смена значения атомарна; явная очистка при optional. **LoV multi:** checkbox selection, список выбранных значений, количество, удаление отдельного значения. При табличном picker поиск не теряет скрытые выбранные элементы. В нескольких колонках MAY выводить ID, имя, тип, статус, систему; конфигурация задаёт состав и фильтры.

**Reverse usage:** список «Используется в…» — derived read-only collection. Пользователь не выбирает её множественность и не редактирует список как собственные refs; изменения через объект-источник. Forward refs и reverse usage получают разные подписи и действия.

Properties pane: секции «Основное», «Атрибуты», «Связи», «Использование», «История» по реальным возможностям. ID/path копируются; read-only объясняется; provenance и pending changes видны. Зависимость атрибутов объявляется рядом с полем, не только в toast.

## 9. Frade Draw и менеджер потоков

Холст: нейтральный `diagram.canvas`, малоконтрастная сетка по настройке, ясное выделение, стабильная геометрия. Цвета фигур и потоков не должны конкурировать с UI-командами. Selection, focus и domain status — отдельные слои. Толщина hover/selection меняет overlay, а не persisted route/shape.

Repository-bound диаграмма MUST показывать связь с объектом, источник атрибутов и разрешённые override. Standalone MUST явно показывать отсутствие привязки и допускать ручную визуальную настройку. Копирование из bound в standalone не создаёт скрытых write-back операций. Разрыв привязки — явная команда с объяснением результата.

Новые/изменяемые domain mappings определяются конфигурацией: статус → цвет+иконка/маркер+подпись; направление потока → стрелка+доступное направление в свойствах. MUST NOT кодировать состояние только красным/зелёным. Диаграмма имеет легенду, экспорт и theme-independent печатный mapping. Смена темы интерфейса не переписывает сохранённую семантику диаграммы. Печатная схема должна быть различима без фона приложения.

Любая интерактивная ручка имеет hit area минимум 24 CSS px либо документированное соответствие допустимому WCAG-исключению, проверенное на конкретном случае. Если hit areas пересекаются, обеспечить zoom, иной способ выбора или клавиатурную команду. Визуальная ручка MAY быть 6–8; hit area не меняет положение anchor. Selection/hover MUST NOT менять endpoint, маршрут или routing constraints.

Перетаскивание показывает preview и итоговую геометрию согласованно; Esc отменяет; завершение даёт одну undo-операцию. Style guide не определяет routing algorithm и не отменяет INV-007/INV-008. Изменения route/segment contracts выполняются только в соответствующих OpenSpec changes.

Для accessibility холст имеет синхронизированный список объектов/связей, операции выбора и редактирования с клавиатуры и понятные текстовые названия. Миникарта не является доступной альтернативой сама по себе.

**Жгут потоков:** панель показывает все потоки между системами, их атрибуты, включение в текущую диаграмму, поиск/фильтры/сортировку и режим «Только включённые». Действия «Исключить из диаграммы» и «Удалить из репозитория» MUST различаться. Локальный поток помечается «Только в диаграмме»; «Добавить в репозиторий» — отдельное действие с проверкой. Selection строки не включает поток автоматически. Итоговое число включённых потоков видно на жгуте/в панели.

## 10. AI-приложение

AI использует существующую оболочку. Sidebar: «Новый чат», закреплённые проекты/чаты, проекты, последние чаты; поиск при достаточном объёме. Чат открывается в редакторе; переключение раздела сохраняет черновик, вложения и scroll position. Тема, меню, вкладки и диалоги — общие.

Сообщения — спокойные текстовые блоки с явным автором и действиями, без ярких messenger-bubbles. Ширина чтения по умолчанию до 760; центрирование внутри широкой editor group. Код — mono, копирование и горизонтальная прокрутка. Composer имеет видимый режим/placeholder, attach controls, выбранную модель, send/stop. Отправка по умолчанию Enter, Shift+Enter — перенос; настройка Ctrl+Enter MUST быть доступна и показываться в подсказке. Нельзя отправлять сообщение при незавершённом IME composition.

Streaming не перетягивает пользователя вниз, если он прокрутил вверх; показать «К последнему сообщению». Ошибка сохраняет введённый текст, вложения и частичный ответ с явным состоянием. Screen reader получает батчированные обновления, не announce каждого токена.

При добавлении данных репозитория MUST отображать состав контекста и получателя/провайдера до отправки в соответствии с утверждённой политикой подключения. AI-изменение объектов представляется как предложенный diff с явным применением; текст ответа не означает, что данные уже изменены. Это UI-требования, не обещание наличия конкретных интеграций или полного функционального паритета с ChatGPT.

## 11. Тексты и обратная связь

| Ситуация | Формулировка |
|---|---|
| Создание | «Создать объект», «Новый чат» |
| Ошибка сохранения | «Не удалось сохранить объект. Проверьте подключение и повторите попытку.» |
| Конфликт | «Объект изменён в репозитории. Сравните версии перед сохранением.» |
| Нет результатов | «Объекты не найдены. Измените запрос или сбросьте фильтры.» |
| Detach | «Исключить поток из диаграммы» |
| Delete | «Удалить поток из репозитория» |

MUST писать коротко, активно, с конкретным действием. Не выводить пользователю внутренние названия классов, stack trace и gate-state вместо объяснения; подробности доступны в раскрываемом блоке/логе. Нельзя писать «Произошла ошибка» без действия или «Успешно!» для каждой малой операции. Текст не обвиняет пользователя. Термины «объект», «связь», «поток», «жгут», «репозиторий», «проект», «диаграмма» имеют единый смысл во всех разделах.

Пользовательские даты — locale + явная timezone при необходимости; machine timestamps — ISO 8601 в модели. Тексты локализованы ресурсами; длина проверяется на русском и английском, включая увеличение на 30%. Числа и форматирование не конкатенируются вручную.

## 12. Доступность

Цель — WCAG 2.2 AA для применимых веб-критериев и соответствующего renderer UI Electron. Это требование реализации; данный пакет не является сертификацией готового приложения.

| ID | Обязательное правило |
|---|---|
| A11Y-001 | Обычный текст ≥4.5:1; крупный текст ≥3:1 по определениям WCAG. Служебный мелкий текст также ≥4.5:1. |
| A11Y-002 | Существенные границы интерактивных контролов и графические признаки состояния ≥3:1 к прилегающим цветам. Декоративные разделители исключены. |
| A11Y-003 | Видимый keyboard focus; не скрыт sticky/overlay. Ring минимум 2, не заменяется hover. |
| A11Y-004 | Релевантные pointer targets ≥24 × 24 CSS px либо соответствуют конкретному исключению 2.5.8. Для coarse pointer минимум 44. |
| A11Y-005 | Все действия доступны клавиатурой; нет keyboard traps, кроме управляемого modal. |
| A11Y-006 | Dragging имеет альтернативу без dragging: меню, поля координат или команды. |
| A11Y-007 | Semantics и состояния соответствуют фактическому поведению, не только внешнему виду. |
| A11Y-008 | 200% text zoom; reflow для применимых областей; reduced-motion; forced-colors. |
| A11Y-009 | Labels/ошибки связаны с полями; status updates объявляются с контролируемой частотой. |
| A11Y-010 | Canvas имеет функциональную альтернативу; форма редактирования — часть keyboard-пути. |

Проверка контраста из пакета покрывает перечисленные пары токенов. Контраст реальных компонентных состояний, focus на сложных фонах, скринридеры и приложения отдельно проверяются при внедрении. Disabled-элементы имеют допустимые WCAG-исключения, но текстовое объяснение причины SHOULD оставаться читаемым.

## 13. Организация кода

Целевая раскладка, адаптируемая после аудита monorepo:

```text
docs/ui/Frade-UI-Style-Guide.md
docs/ui/QA-Checklist.md
docs/ui/decisions/
packages/ui/tokens/tokens.json
packages/ui/styles/tokens.css
packages/ui/src/components/
packages/ui/src/patterns/
packages/ui/stories/
scripts/ui/generate-tokens.py
scripts/ui/check-tokens.py
openspec/changes/<ui-change>/specs/<ui-capability>/spec.md
openspec/changes/<ui-change>/evidence/
```

Имена и пути MUST сопоставляться с реальным проектом до создания. Не создавать второй UI-package, если единый слой уже существует. Зависимость: feature → patterns/components → tokens; UI MUST NOT импортировать feature-модули. Domain model и persisted diagram semantics не зависят от темы UI. Shared components не знают провайдера AI или формата конкретного репозитория.

MUST подключать токены один раз у корня приложения, передавать тему и плотность единым механизмом, размещать overlays в одном управляемом host и использовать shortcut registry с контекстом. Inline styles MAY задавать runtime coordinates/widths/zoom, но не подменять палитру и размеры стандартных контролов.

## 14. Обязательный процесс любого UI-change

1. **Контекст.** Прочитать root/scoped AGENTS, этот guide, текущие токены, shared UI и approved OpenSpec scope. Записать версию guide и исходный commit.
2. **Постановка.** Описать affected screens/components, сценарии, состояния, темы, плотность, keyboard/a11y и применимые FDS/A11Y IDs. UI изменений нет — отметить `NOT_APPLICABLE` с причиной.
3. **Планирование.** Использовать существующие компоненты. Если нужен новый паттерн, сначала описать общий контракт и при необходимости ADR. При spec conflict — определить минимальное противоречие и предложить разрешение; существующий gate остаётся блокирующим.
4. **PRE gate.** Установленный проектом этап планирования/независимого review MUST завершиться PASS до implementation. Для визуально малой задачи глубина доказательств пропорциональна, но обязательные checks не исчезают.
5. **Implementation.** Только approved scope; tokens-first; состояния и клавиатура; без скрытого redesign соседних областей.
6. **Проверки.** Выполнить релевантные unit/interaction/BDD, проверку токенов, a11y и визуальное сравнение для затронутых представлений. Простая смена отступа не требует искусственного теста, повторяющего CSS; достаточно необходимых project checks и визуального QA.
7. **POST gate.** Представить diff, rule mapping и проверяемые evidence. FAIL/BLOCKED запрещают переход; NOT_RUN не равен PASS. Baseline нельзя автоматически перезаписывать, чтобы убрать падение.
8. **Завершение.** Сохранить evidence/fixtures и выполнить review/archive/commit по действующему OpenSpec workflow. Не переходить к следующему последовательному этапу до закрытия текущего.

Включение `AGENTS-UI.fragment.md` помогает Codex читать правила, но само по себе не даёт технической гарантии. Реальная обязательность: компонентный слой + lint/CI + защищённые branch checks + reviewers. Для локального режима без CI gate исполняется локально и его отчёт сохраняется; статус `LOCAL_ONLY` MUST быть виден, автоматическую защиту ветки утверждать нельзя.

### 14.1 UI compliance gate

| Проверка | PASS требует |
|---|---|
| Scope | Изменения укладываются в разрешённые пути и approved contract. |
| Tokens | Нет новых feature-level цветовых литералов; generated CSS соответствует JSON; проверенные пары проходят контраст. |
| Components | Переиспользование shared UI либо описанный новый контракт; нет второй визуальной системы. |
| States | Проверены все затронутые состояния, включая ошибки/dirty/loading при наличии. |
| Keyboard | Можно пройти основной сценарий и выйти/отменить без мыши. |
| A11y | Нет относящихся к изменению нарушений обязательных правил; применимые исключения документированы. |
| Visual | Light/dark/high contrast и compact/comfortable для изменённых экранов; отсутствие clipping при resize/zoom. |
| Regression | Не изменены данные/dirty-state при навигации; обязательные проектные тесты пройдены. |
| Evidence | Реальные результаты с датой, окружением, командами, commit и ограничениями. |

Только шесть фотографий разных тем не заменяют проверку поведения. Если инструменты недоступны — указать BLOCKED или NOT_RUN для соответствующей проверки; не придумывать успешные результаты.

### 14.2 Изменение правил и исключения

Новые оттенки, токены, варианты или паттерны сначала описываются в общем слое и документе. ADR содержит проблему, рассмотренные варианты, принятое правило, затронутые IDs, область, проверку и миграцию. Routine выбор значения из существующих токенов не требует отдельного разрешения пользователя.

Исключение из MUST допустимо только через принятое изменение самой спецификации в действующем workflow; временное исключение имеет owner, причину, срок/этап закрытия и scope. Слова «так красивее» или «модель предложила» не являются обоснованием. Изменение лого согласуется с бренд-контрактом; стайл-гайд не создаёт новую версию бренда молча.

Версии: patch — уточнение текста; minor — совместимый новый компонент/роль; major — изменение существующего поведения/токен-контракта с планом миграции. Версия фиксируется в guide, JSON и evidence. UI-owner/reviewer — роль, назначаемая в реальном проекте, а не выдуманное имя.

## 15. BDD/TDD для внедрения

BDD-контракты приведены в `ui-contracts.feature`. Они покрывают тему, плотность, фокус, клавиатуру, dirty tabs, LoV, flow detach, standalone/bound и AI. Файл — спецификация, не исполняемый тест без step definitions и adapter реального приложения.

TDD по слоям: theme resolver → token generation/validation → state reducers для tabs/selection → доступные shared components → workbench integration → доменные представления. Unit должны проверять последствия состояния, а не копию CSS. Interaction tests проверяют открытие, сохранение/отказ, фокус и команды. E2E проверяет сквозные сценарии с реальным editor lifecycle. Visual regression проверяет утверждённые screen states на фиксированных viewport/font/DPR; исключает только динамические timestamps/streaming, не область ошибки целиком.

Не требуется писать все перечисленные тесты для каждой правки. Требуется доказать применимые контракты и выполнить обязательные проверки текущего change.

## 16. Порядок внедрения в Frade

Подключаемые темы и плагины реализуются по отдельному обязательному контракту `Themes-and-Plugins-Spec.md`: P01–P07, manifest, installer, resolver, extension host и contribution APIs. Статический `tokens.css` — исходная встроенная палитра, а не реализация ThemeService. Импортированная theme data проходит registry/validation; feature-level запрет HEX не запрещает HEX внутри валидируемого theme package.

1. Разместить пакет во временном `_input/frade-ui-style-guide-v1/` и запустить `CODEX-Implementation-Prompt.md`. `_input` — вход, не постоянный источник правил.
2. Аудитировать текущие shared UI, темы, иконки, overlays, shortcuts и брендовые активы; зафиксировать baseline без изменения функциональности.
3. Создать отдельный OpenSpec change для нормативной основы, определить реальные пути, перенести guide в `docs/ui`, встроить fragment в AGENTS без удаления существующих правил.
4. Подключить tokens и общий theme/density resolver; проверить light/dark/HC/system и сохранить состояние пользователя.
5. Последовательно мигрировать shell → basic controls → tree/tabs → forms/tables/LoV → Draw/flow manager → AI. Между этапами сохранять gates; порядок MAY адаптироваться к утверждённому roadmap.
6. Добавить lint правил цветов/иконок, token check, применимый accessibility/visual CI и UI compliance report. Проверить фактическую защиту merge.
7. Убрать дублирующиеся стили после прохождения gates. Не смешивать миграцию с routing refactor или изменением Repo Core persistence.

Перенос по одному feature допускает временные старые экраны, но изменяемая область должна использовать новый контракт. Дизайн-система становится реализованной после появления работающего shared UI, документации компонентов, тестов и gates; наличие этого Markdown не означает завершение миграции.
