## Decisions: resolver and durable settings

1. **Resolver / registry.** Import existing generated palettes without changing them. Builtin stable IDs frade.builtin/light, frade.builtin/dark, frade.builtin/high-contrast; registry reserves these immutable offline entries. External in-memory descriptors are validated data, not installed packages. Stable publisher.name/local IDs do not depend on version/path/label. Native input accepts known role IDs and HEX6; unknown roles are diagnostic-only and never injected. Invalid values produce explicit issues without arbitrary CSS. Use all 31 roles and the existing fixed 34 contrast-pair definitions; a runtime pure constraint table must be compared to the unchanged foundation table, not diverge. Precedence builtin -> enabled selected descriptor -> user global -> selected ThemeId override -> explicitly enabled workspace override. Fixed pair order restores both roles from builtin for at most ten passes, then full builtin FALLBACK. Inputs remain unmutated; outputs/diagnostics copied and deeply frozen. Density is separate. Forced-colors final system keyword mapping overrides presentation values even with explicit Light/external overrides; do not persist system keywords as user HEX. Installed-package enable/remove/version lifecycle remains P02.

2. **Persistence / startup.** One user/profile settings DTO (version 1) stored in a fixed userData presentation-settings.json, with theme System by default, preferredLight/Dark/HC IDs and density compact by default. Profile here means the existing selected Electron userData root; P07 owns multi-profile management. Opt-in workspace override is resolver data only, with no automatic workspace file reads or writes and no trust escalation. Unknown/stale IDs repair to offline builtin of kind with diagnostics, not a phantom installed theme. Main validates every DTO before and after IPC; separate channel/exposure preserves the existing window.frade health keys. Authorize the existing window/main frame/trusted page; deny child frames, forged revisions, arbitrary paths, unknown fields and oversized payloads. Serialize commits using host revision/CAS. Write a fixed-path staged file, flush and atomic rename; prepare must never replace current settings. On write failure read back authoritative state and restore old persistent/presentation selection; report unknown outcomes instead of falsely claiming rollback. Startup reads/validates before showing the window; initialize builtin/root metadata before first app paint, restore valid user selection before showing normal UI, default with visible diagnostics on malformed/unreadable settings. No repository/workspace/domain settings write, API-version rewrite or global configuration mutation.

The host queue/linearization and bootstrap handshake below refine persistence; when state cannot be proven the system stays in explicit recovery rather than claiming rollback success. A synchronous renderer call reads only validated in-memory boot data, never filesystem. An external descriptor registry is in-memory data only; installing/enabling/removing packages remains P02.

### B04: transaction protocol, ownership and linearization

Closed states: IDLE(committed snapshot + durable host revision); PREPARING(intent,generation,membership); READY(all prepared); BARRIER_AWAIT_PAINT; APPLYING; PERSISTING (commit only); RECONCILING_UNKNOWN; COMPENSATING; PUBLISHED (preview or durable); CANCELING; RECOVERY_BLOCKED. Every message contains version1, bounded requestId, window sessionId, intent generation, transactionId, snapshot revision, membership version and exact phase. Unknown fields/roles/phase/foreign origin/source/window/frame generation reject. Payload <=32KiB and known 31 roles only. Runtime schema is separate from the existing health API.

Host owns a single serialized intent/persistence queue. Renderer sends announceIntent before starting preparation; host acceptance assigns a monotonic intent generation. There is no claim that a remote user gesture cancels an already linearized OS rename before host receives it. Before each stage/rename the host verifies the current accepted generation/CAS. Once a rename has started it must be reconciled in this queue; no concurrent rename/compensation may run. The durable linearization point is successful atomic rename of the validated settings record; acknowledgement is emitted only after readback validates its transaction/generation/revision. If C arrives during A's rename, A is never published as a current UI selection: the host completes/readbacks A, then performs owned compensation or commits prepared C before allowing reveal. A cannot write after C's durable commit or acknowledgement because all these transitions share the same queue. If C preparation fails, restore the last published durable snapshot through a new host-owned compensation revision before exposing it; no old caller owns an unconstrained rollback write.

| Phase / event | Required transition and visible/durable effect |
| --- | --- |
| announceIntent A accepted | Reserve generation; invalidate older uncommitted handles; no presentation/settings write |
| prepare all ready participants | Side-effect-free handles, captured membership; stale result disposed; prepare failure -> cancel to last committed |
| begin barrier | Full workbench client-area neutral busy curtain is actually painted before any participant applies; preserve documents/focus/editor identity |
| commit all | Prepared handles apply one revision; ACK means applied phase AND a subsequent view paint, not message receipt; no setting write for preview |
| preview complete | Reveal preview only when all required ACKs match; durable selection stays last committed |
| Enter / durable persist | Keep barrier until host queue rename/readback success and all participant revisions match; publish one did-change then reveal |
| new C before/after prepare or during apply | Mark A stale; keep/re-enter barrier; cancel A handles, compensate applied participants and any authoritative settings outcome, then prepare current C |
| membership changes in any non-IDLE phase | Invalidate membership, keep barrier, reconcile any durable write and compensate before restarting; never just ignore a new/removed required participant |
| participant joins | Attach hidden with last committed state; becomes visible only after validated current revision ACK and service membership acceptance |
| participant leaves/navigates/disposes | Invalidate its frame generation; pending ACK rejected; service aborts/reconciles current transition; closed documents remain caller-owned, theme never remounts them |
| timeout/persistence failure/unknown response | Readback authoritative host transaction; restore last committed through serialized CAS compensation if outcome permits; retain RECOVERY_BLOCKED if outcome cannot be proven |
| Esc/outside/owner cancellation/window close | Invalidate active intent, reconcile its queue, restore last committed required participants and authoritative settings, cancel preview; window close resumes existing dirty guard only after cancellation outcome |
| rollback refusal / unavailable frame | RECOVERY_BLOCKED with visible accessible error and safe recovery action; no reveal of mixed state or success event; dirty editors retained |

Timeouts: prepare per required participant 2s; commit/rollback applied-paint ACK 2s; host write/readback attempt 5s; reconciliation max5s; bootstrap ready handshake max5s. Timeouts are errors with phase/participant/intent diagnostics, never ignored. They are failure deadlines, not the p95 budget. Tests use controlled barriers/fake time at unit layer, actual bounded runtime at integration. No retry loop continues indefinitely; one safe reprepare for membership churn then an explicit canceled/recovery result for ongoing churn.

**Observable atomicity / native window:** all Frade web-content consumers including titlebar DOM are under the full neutral curtain; OS-owned decoration/caption buttons are outside the semantic token consumer contract and remain the unchanged platform surface in P01. Remove native-window theme mutation from P01 participants and defer native background/titlebar-overlay token adoption to shell/basic-controls with its own compositor evidence. This is explicit P01-NATIVE-CHROME-LEGACY-01, owner shell/basic-controls, expiry before that stage POST/archive. It is included in the recorded human scope acceptance and MUST be disclosed as a limitation; do not claim the current fixed native caption/background is themed. No visible partially mixed web-content revisions may be exposed.

**Bootstrap handshake:** main reads/validates profile settings and resolves pure leaf builtin/preferred data before window load; preload exposes a copied validated boot snapshot through the separate presentation API (host in-memory synchronous bootstrap response, bounded <=32KiB, authorized main frame only, no per-call filesystem work). Main may call show only after both Electron ready-to-show and matching presentationReady; it must replace the existing unconditional show hook.
