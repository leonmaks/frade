## Decisions

Create platform-neutral package DTO/schema and injected filesystem/journal service, with concrete Electron file picker/authorized installation root in Main/service. Do not reuse repository journals or write workspace. Frade is currently 0.1.0; initial package compatibility uses supported application range >=0.1.0 <0.2.0 and a separately versioned Frade API baseline 1.0.0. Parse real semver. Keep original sample archive byte-identical as a future fixture: its >=1.0.0 <2.0.0 Frade range is incompatible with current runtime and must reject; create explicitly derived compatible positive fixture, recording both hashes. Native ZIP limits: 50 MiB compressed/200 MiB expanded/10000 entries/ratio100/depth32, reject traversal/absolute/symlink/case duplicates/Windows reserved/NUL. Hash exact archive SHA256, do not infer trust from publisher. Versioned staging + old/new registry snapshots + journal phases. Validate before pointer swap; crash-at-each-phase loader restores last commit/cleans staging. Disable/update/remove atomically unregister and fallback via P01. Cleanup after handles release; Windows locks retain honest pending state. Declarative packages never execute scripts. Installer leaves active theme unchanged until explicit picker selection. Extension details/diagnostics view uses shared contract.

## Archive and schema validation

Use explicit yauzl3.4.0 for asynchronous central-directory/lazy entry streaming, strictFileNames true and validateEntrySizes true; semver7.8.5 for strict identity/version/engines checks, @types/yauzl3.4.0 and @types/semver7.8.0 for TypeScript only. Registry versions/integrities and official docs are saved in evidence/p02-accepted-planning-20261010T002712Z/dependency-selection.json. The approved parsers are now installed by the archive-validator checkpoint; this amendment adds no dependencies. [Yauzl primary documentation](https://github.com/thejoshwolfe/yauzl) and [node-semver](https://github.com/npm/node-semver) support this choice. A bespoke ZIP/range parser was rejected because format/compatibility corner cases belong in established parsers; parser output alone is not our security gate.

- SHA256 is computed from the same bounded immutable archive bytes used for validation/staging, never a reopened mutable external path. Copy chosen input to owned staging via safe handle, abort at compressed50MiB; do not trust extension/sizes/publisher. Header/entry/stream checks enforce total actual expanded200MiB, entries10000, actual per-entry and aggregate expansion ratio100 and depth32. Fail before writing outside staging; abort streams and close handles on every error.
- Reject absolute/drive/UNC/backslash/traversal/dot segments/empty ambiguous segments, NUL/ADS, reserved Windows names including extensions, trailing dot/space, case-insensitive duplicate file/directory and file-vs-parent conflicts, symlink/device entries, unsupported encryption/compression/multi-volume, malformed metadata/local-vs-central disagreement and CRC corruption. Verify actual CRC32 and byte counts in application if the selected parser does not. Directories are accounted; ZIP64 bounded safe integers are checked, not silently truncated. Limits cannot be bypassed by header under-reporting, data descriptors, repeated paths or extra fields. Actual overflow fixtures assert bytes/calls/outside-root unchanged.
- Staging roots/versioned dirs and every ancestor must be real directories within one authorized installation root. No symlink/junction traversal; exclusive writes/no path replacement; file handle and reparse tests on Windows. Do not recursively remove a computed root without verifying absolute containment. Deny altered installed manifests/data/hash at startup with per-package diagnostics.
- Root package.json requires stable publisher.name, version and valid engines.frade/fradeApi ranges, declarative kind, empty capabilities and known theme-only contributions. Current app0.1.0/API1.0.0; compare actual runtime/API against package ranges, no version bump or rewritten original sample. Reject browser/native executable fields or unsupported contributions with explicit compatibility errors; a future executable contribution/capability increase is denied before use in this stage. Known role data conforms to canonical native theme schema; unknown role/schema errors are explicit, no arbitrary CSS/font/spacing/URL/JS injection. Theme kind/path/ID duplicates and package namespace are checked; do not mutate source theme data during contrast repair.
- Native manifest and per-theme bounded JSON validation use explicit owned plain data/schema checks, not eval. Package metadata lengths/JSON limits stay below archive limits; no HTML rendering of descriptions. Present exact source file/hash and unsigned provenance, never Verified Publisher.

## Transaction, commit point and startup recovery

Installer serializes operations against one registry revision. Content-addressed version dirs keep exact immutable bytes for current and retained previous versions; one active version per ID. Journal contains bounded validated transactionID, old/new registry snapshots, exact package hashes/version locations, old/new durable presentation records, phase and cleanup tasks. Package storage/journal is separate from repository journals and workspace.

Phases: STAGING -> VALIDATED -> PREPARED -> SWAPPED -> PRESENTATION_ACK -> COMMITTED -> CLEANUP. Persist each intent before its side effect with file sync and atomic same-directory replace; acknowledge commits only after durable committed marker and consistent registry/presentation. Windows file sync/rename limitations are disclosed and failures remain REFUSED/UNKNOWN/BLOCKED, never assumed durable. Do not use two independent journals with inconsistent startup decisions. Recovery validates journal identity/hash/path/phase and uses one coordinator to restore registry and presentation before first paint/window ready. Corrupt/ambiguous journal is RECOVERY_BLOCKED with recoverable old bytes preserved, not silent reset.

- Before swap, validate and prepare registrations/fallback/consumer quiescence. Cancel pending preview through existing P01 transaction; synchronize renderer membership and generation without killing/recreating document editors. Active affected-theme update, disable, uninstall or rollback prepares P01 participants and replacement selection; package install that does not affect an already selected theme leaves selection/snapshot/settings bytes unchanged.
- Publish new registry revision only with ready candidate registrations and P01 prepared participant acknowledgements. Keep neutral existing P01 barrier until renderer/Main settings and committed installer generation agree. Failure before COMMITTED restores old registry/version/registrations plus prior durable presentation, quiescence and selection; old package bytes retained. Late/duplicate ACKs never commit another transaction. Failure/UNKNOWN reconciliation blocks new lifecycle operations; explicit recovery restores last committed state.
- Crash before valid COMMITTED marker rolls back both registry/presentation to old; crash after valid marker retains new and resumes cleanup. Test interruption after each durable phase and each side effect, including gap between registry swap and presentation persistence, committed marker and replies, and missing retained files. Reopen a fresh loader over actual temp filesystem; separately execute killed-process recovery fixtures rather than treating thrown exceptions as real crash evidence.
- Explicit retained-version rollback uses actual stored bytes and compatibility validation. If prior bytes are absent/changed, return unavailable diagnostic and keep current, not magic recreation. Concurrent operations use expected revision and serialized queue; delete/update races reject stale requests without duplicate active versions.

## Lifecycle and UI consumer contract

P02 installs only declarative native color themes. Built-ins are immutable/offline; no executable host, icon registry, custom editor implementation, VS Code import, registry network or profiles are implemented. The P02 injected lifecycle guard/fallback ports must veto an unsafe dependent editor and coordinate all registered presentation dependencies; this preserves the specified icon/editor obligations for future consumers without pretending those providers are already installed. Tests exercise blocked/save-failure/cancel and successful guard behavior with no silent force removal. Nonempty capabilities/unsupported contributions reject before use, retaining old version; future grants/UI belong to their owning executable host/policy change.

Install makes choices available without selecting them. Update an explicitly active stable ThemeId prepares its new palette through P01; missing/disabled theme chooses built-in of the same resolved kind while preserving mode/density and other preferences. Explicit user removal displays replacement and confirms; successful fallback removes missing preferred ID only in coordinated durable transaction. Re-enable does not silently reselect removed preference. Original P01 controls remain unchanged; new P02 regression assertions verify current integration rather than rebasing raw historical evidence.

Physical cleanup is after commit and handle release. Locks produce CLEANUP_PENDING with retry diagnostics; record logical registration removal separately from physical retained files. Never show physical deletion success while bytes remain. Startup retries only bounded safe pending cleanup, preserving at least required current/rollback bytes; missing previous bytes are reported.

Workbench receives an injected portable extension client, switches sidebar and details surface without unmounting active dirty editors, and registers Ctrl+Shift+X in existing shortcut context. Reuse Codicons, root tokens/density and managed overlay host. Sidebar search/installed/category, selected package details, install/update-from-file, enabled state, disable/remove/retained-version rollback and truthful local diagnostics. Network update checking is explicitly unavailable until P07; local update from file works offline. Show publisher as declared, hash/source/compatibility and pending cleanup. Empty/loading/error/no-results/offline/blocked states are real; labels, keyboard actions and status announcements bound to current generation. Actions must reflect supported operations and busy transaction state; no enabled button that merely simulates success.

### Root binding and race closure

Supported first backend: local fixed NTFS on Windows x64 with an existing compatible .NET Framework CLR/compiler. Reject UNC/network, FAT/exFAT/ReFS, unsupported architecture/CLR and ambiguous volume mapping; no automatic fallback. Main binds its dedicated userData/extensions root once for one session/generation; renderer cannot choose root. Selected package input is read by the existing authorized Main picker path and transferred as owned bounded bytes; the helper never opens that external path. Ancestor metadata handles are needed only to establish the authorized root, not to read ancestor files. Test roots are exclusively owned temporary fixtures.

1. Resolve the drive to its volume GUID, confirm fixed NTFS and store volume identity. Open the volume root directory (not a raw device) and walk each single validated component to the installation root. Each directory open uses NtCreateFile with RootDirectory equal to the already retained parent handle, FILE_DIRECTORY_FILE, FILE_OPEN_REPARSE_POINT and synchronous options, without backup privilege/elevation. Reject empty/dot/dotdot/ADS/device/reserved/ambiguous components, reparse/other special attributes and case-sensitive directory mode. Validate directory type, final volume/name and file identity from the returned handle, never only lstat. Retain each checked handle with FILE_SHARE_READ only, denying write/delete sharing; existing incompatible writer/deleter yields REFUSED before any effect. Missing installation root may be created exclusively relative to a checked parent, then its returned handle validated; missing/untrusted outer ancestors are never created. There is no unlocked check-then-path-open window.
2. Descend below root using only one-component parent-handle-relative opens/creates and retain checked parents until the operation and transaction release boundary. FILE_OPEN_REPARSE_POINT ensures the object itself is examined before traversal; every returned directory is rejected if reparse. Handle-relative addressing prevents changed drive letters or textual ancestor substitutions from selecting another root; retained identities/no-delete sharing prevent replacement. Parent reparse mutation/previous writers must be refused or proven unable to redirect handle-relative operations. Actual adversarial fixtures cover both rename replacement and in-place reparse mutation; a failed race closure is a blocker, never a string-prefix workaround.
3. Create files with FILE_CREATE/CREATE_NEW, non-directory/reparse-open/write-through options, bounded chunk writes and no write/delete sharing. Validate ordinary file, same volume/parent, single hardlink and actual byte count/hash via the held handle; reject existing leaves/reparse/hardlinks/devices/ADS. Read only checked ordinary files via held handles with bounded actual counts; reject changed installed content. Native ABI layouts use pointer-size-correct offsets and checked NTSTATUS/Win32 return values. No suppressed error, buffer overflow or unbounded allocation.
4. Renames use the held source handle with DELETE access and SetFileInformationByHandle(FileRenameInfo) targeting a single validated basename relative to the retained target-parent handle. No reopen-by-path, cross-volume copy, delayed reboot, arbitrary rename flags or shell is allowed. Source and target must be same-volume checked ordinary objects; journal replacement is same-directory. Old journal bytes/hash remain in coordinator recovery data. Target conflicts/reparse/special objects fail closed; path replacement of target cannot redirect writes because only its directory entry is replaced, never followed. Do not release root/parents during commit or between staging validation and effect.
5. Cleanup enumerates only held checked directories with bounded entry/count/depth, opens every child itself without following reparses and deletes the opened object by handle. Retain parents, check volume/object identities; do not recursively delete a computed text path. Release source/consumer handles at approved cleanup boundary. Sharing conflicts return CLEANUP_PENDING, never physical-deletion success. Shutdown/EOF/helper death releases OS handles and makes session unusable; new generation must recover before another operation.

### Journal persistence and supported guarantee

The unchanged transaction contract requires a durable coordinator intent before every side effect and valid COMMITTED marker before ACK. For same-directory journal replacement, create exclusive write-through ordinary temp file, write exact bounded journal bytes and FlushFileBuffers on the held writable handle; rename that same held object relative to the checked parent as above. After rename, make a write-through write of the same exact journal contents on the same held object, FlushFileBuffers again, and verify identity/final name, size and SHA256 before ACK. The post-rename write is idempotent and changes no semantic bytes; a crash before completion is reconciled from validated old/new hashes and phase, never assumed committed. NTFS metadata flushing associated with a write-through write is the selected documented OS mechanism; generic rename return or Node fsync(directory) is not our mechanism.

Supported claim is checked Windows/NTFS write-through + explicit file flush and same-directory handle rename, with process-crash recovery proved by real kill/reopen at all phases/effects. Full OS/storage power-loss behavior is NOT_PROVEN; do not advertise unconditional hardware durability. No raw-volume flush requiring admin and no synthetic directory-sync success. This is an API-level persistence guarantee subject to OS/storage honoring flush/write-through; report the exact capability/preconditions. If the runtime cannot prove these calls/identity/race semantics in its owned capability fixture, it returns BACKEND_UNAVAILABLE/REFUSED before installer use. If an error, timeout or helper death occurs after any effect but before durable ACK, return UNKNOWN, preserve old/new bytes, block new transactions and reconcile through startup journal; never report successful install. If stronger unconditional power-loss proof is later required, stop for its own explicit decision rather than weakening this contract.

### Closed transport, limits and lifecycle

No shell: spawn the verified helper directly with hidden window and dedicated stdio; no network, commands, executable package loading or generic host paths. Main chooses root and host-generated session/generation. One bind request, then version1 closed operations bind/capabilities/mkdir/read/write-open/write-chunk/write-close/replace/list/remove/dispose; operation-specific exact schemas reject unknown fields. Helper returns opaque internal handle IDs bound to session/generation, never OS handles to renderer. Frames are newline-delimited UTF-8 JSON max128KiB, chunks max64KiB decoded (strict base64), paths max4096 characters/depth32, directory entries10000, per-file/aggregate bytes no greater than unchanged archive50MiB/200MiB; actual writes/counts and buffers are bounded. State schema/journal metadata max1MiB; larger archive transfer is chunked, not one giant JSON. Validate version, monotonically increasing unique requestID, session, generation, operation, sequence, expected offset, deadline and exact field types before effect. Serialize one pending command; duplicate/replayed/out-of-order/expired frames terminate/refuse the session without another effect. No unbounded queues. Use host monotonic deadlines (10s bind/operation, bounded long writes per chunk); replies bind exact request/session/generation. Wrong, malformed, oversized, timed-out or late responses fail closed. Host transport kills/disposes an unusable helper, rejects pending calls and marks UNKNOWN if an effect may have happened; retries are coordinator recovery decisions, never blind repeats. EOF/close/dispose/window lifecycle invalidates all outstanding handles and subscriptions. Tests separately prove wrong-session/generation/deadline/frame/offset/replay, crashes before/after effect and actual handle release.
