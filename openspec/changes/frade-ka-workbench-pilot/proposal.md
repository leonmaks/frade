# Proposal

## Why

Frade уже содержит Repository Core, но пользователь не может открыть существующий KA, просматривать все архитектурные объекты и редактировать их карточки с сохранением в исходные YAML. Этот change реализует сквозной desktop-пилот на предоставленном репозитории и связывает хранение, метамодель и интерфейс в соответствии с модульной архитектурой Frade.

## What Changes

- Добавить отдельный адаптер `sberea` в пакете `@frade/adapter-sberea-yaml`: рекурсивные `imports`, словари сущностей, стабильные идентификаторы, происхождение данных и обратную запись в исходные файлы. `adapter-yaml` сохраняет существующие native-форматы; другие специфичные YAML-адаптеры подключаются через общий контракт и backend registry без изменения UI/Core.
- Для каждого репозитория `sberea` задавать папку метаописания независимо от каталога данных. Сохранять несколько именованных наборов и активный выбор; поддержать перенос папки, изменение пути и проверяемое переключение наборов. Для исходного пилота использовать `_ecosystems_` с entries `kadzo/v2025/entities`, `docs/metamodel` и явным дополнением `tech_params` из v2023. Эти пути являются настройками набора. Сохранять все записи и неизвестные атрибуты, показывать исходные ошибки и неразрешённые ссылки.
- Создать предусмотренные архитектурой `metamodel-config`, `ui-navigator`, `ui-inspector`, `ui-workspace`. Формы строить из effective metadata, включая вложенные поля, ссылки и условные ограничения.
- Реализовать multi-root workspace по аналогии VSCode: добавление, удаление из workspace, переупорядочивание и восстановление нескольких репозиториев с независимыми адаптерами и метаописаниями. Каждый репозиторий — отдельный корень дерева слева; вкладки справа, черновики, ошибки и сохранение привязаны к конкретному репозиторию.
- Максимально точно воспроизвести внешний вид и поведение workbench VSCode: панели, размеры, разделители, иконки, вкладки, меню, фокус, клавиатуру и жесты. Проверять по зафиксированной версии и матрице соответствия, а не по субъективному сходству.
- Расширить публичный API метаданными, диагностикой и событиями; разместить реестр независимых репозиторных сессий в backend/Utility Process, сохранив выбор разрешённых каталогов в Main.
- Проверить полный цикл на изолированной копии переданных данных, включая повторное открытие, сохранность постороннего содержимого и внешние конфликты.

## Capabilities

### New Capabilities

- `sberea-yaml-repository`: отдельный адаптер sberea, полное чтение KA и сохранение изменений в исходный многофайловый YAML.
- `ka-metamodel-import`: импорт внешних схем, UI-метаданных, ссылок и правил из настраиваемых, переносимых и переключаемых папок метаописания sberea.
- `repository-navigator`: несколько корней репозиториев, деревья объектов, проекции и синхронизация выбора.
- `repository-inspector`: динамические карточки, черновики и проверяемое сохранение.
- `repository-workbench`: multi-root workspace, оболочка и взаимодействия по эталону VSCode.
- `desktop-repository-session`: независимые backend-сессии и типизированный транспорт для всего сценария.

### Modified Capabilities

Нет изменений требований трёх опубликованных foundation-спецификаций. Требования независимости Draw, границ пакетов и проверок сохраняются. Change дополняет активный `frade-repo-core`, но не закрывает его незавершённые задачи и не архивирует его.

## Impact

Новые пакеты: `adapter-sberea-yaml`, `metamodel-config`, `ui-navigator`, `ui-inspector`, `ui-workspace`. Изменения затронут `repository-ports`, `repository-application`, `repository-api`, `metamodel-domain/compiler` при необходимости общих контрактов, `runtime-*`, `apps/desktop`, проверки границ и тестовые наборы. Существующие native v1/v2 и standalone Draw остаются совместимыми. Общие YAML-примитивы переиспользуются через публичные границы; sberea-специфика не добавляется в native-адаптер. Название change сохраняется: KA — набор пилота, sberea — вид репозитория.

Фактический источник пилота: `E:/sber.wsp/ka_dzo/KA/root.yaml`. Исследование 2026-09-24 обнаружило 22 импортируемых файла, 138 архитектурных записей 19 типов, отдельные служебные разделы `sber`, четыре записи `tech_params` и семь отсутствующих в KA идентификаторов ПО. Эти числа являются проверяемым baseline конкретного набора, а не ограничениями загрузчика. Исходные пользовательские данные не изменяются для подготовки тестов и не публикуются в удалённые сервисы.
