============================================================
1. BUSINESS CONTEXT
============================================================

UI Frade состоит как минимум из:

LEFT:
Repository Navigator — дерево объектов Digital Repository.

RIGHT:
Diagram Editor — архитектурная диаграмма.

На диаграмме могут присутствовать две системы или подсистемы:

System A
System B

Между ними создается специальная Diagram Edge типа:

Integration Bundle
далее: Bundle / Жгут.

Bundle сам по себе НЕ является Integration Flow.

Bundle является diagram-level representation, содержащим 0..N ссылок на Integration Flow objects из Digital Repository.

Пример:

Repository:

Flow F1: A -> B
Flow F2: A -> B
Flow F3: B -> A
Flow F4: A -> B
Flow F5: C -> D

Diagram D1:

Bundle A-B:
  F1
  F3

Diagram D2:

Bundle A-B:
  F2
  F3
  F4

F1-F4 существуют независимо от диаграмм.

Удаление F1 из Bundle D1 не удаляет F1 из Repository.

============================================================
2. ГЛАВНЫЙ DOMAIN INVARIANT
============================================================

Строго разделить:

A. Repository object existence

и

B. Diagram membership.

IntegrationFlow является canonical repository entity.

Bundle содержит только references на canonical IntegrationFlow entities.

Запрещается копировать IntegrationFlow attributes внутрь Bundle как source of truth.

Conceptually:

IntegrationFlow
    1
    |
    | referenced by
    |
    0..N
BundleMembership

Diagram Bundle:

BundleEdge
  sourceNodeRef
  targetNodeRef
  integrationFlowRefs: RepoObjectRef[]

Используй существующий RepoObjectRef/EntityRef Frade.

Если такого abstraction нет, спроектируй canonical ref, достаточный минимум:

repositoryId
entityTypeId
objectId

Не используй bare YAML path как domain identity.

============================================================
3. ELIGIBILITY RULE
============================================================

Пусть endpoints Bundle:

A
B

Integration Flow может быть включен в Bundle тогда и только тогда, когда:

(source == A AND consumer == B)

OR

(source == B AND consumer == A)

Порядок endpoint'ов Bundle не определяет направление Integration Flow.

Bundle является недирекционным контейнером для directed flows.

Функция:

isFlowEligibleForBundle(flow, A, B)

должна сравнивать canonical repository object refs.

Она должна быть pure domain function и иметь полное unit-test покрытие.

============================================================
4. SYSTEM/SUBSYSTEM SEMANTICS
============================================================

MVP использует EXACT endpoint matching.

Если Bundle соединяет:

System A
Subsystem B1

eligible только flows, у которых source/consumer прямо ссылаются именно на эти objects.

НЕ делать автоматически:

"System A включает все child subsystems".

Иерархическое descendant expansion не входит в текущий scope.

Архитектура query API при этом не должна запрещать добавить такой режим в будущем.

A -> B
B -> A

============================================================
9. MEMBERSHIP CHECKBOX
============================================================

Checkbox в первой колонке — это НЕ generic table row selection.

Это domain property:

"показывать данный repository Integration Flow внутри данного Bundle на данной Diagram".

Checked:

flow ref существует в bundle.integrationFlowRefs.

Unchecked:

flow ref отсутствует.

Click checked -> unchecked:

remove membership only.

НЕ удалять Integration Flow из Repository.

Click unchecked -> checked:

добавить RepoObjectRef в Bundle.

Duplicate references запрещены.

Membership mutation должна:

- использовать Diagram command stack;
- быть undoable;
- быть redoable;
- mark diagram dirty;
- корректно сериализоваться;
- корректно восстанавливаться после reload.

НЕ нужен отдельный Apply button.

Membership checkbox изменяет diagram state сразу через command.

============================================================
10. UNDO / REDO
============================================================

Обязательные commands:

AddFlowToBundleCommand
RemoveFlowFromBundleCommand

или equivalent existing generic commands.

Поведение:

check F1
=> F1 появляется в Bundle.

Undo
=> F1 исключается.

Redo
=> F1 снова включается.

Все membership mutations должны быть atomic diagram commands.

Выбери pattern, наиболее согласованный с существующим UI Frade.

User должен иметь возможность увидеть ВСЕ attributes объекта, а не только columns.

Attributes должны строиться metamodel/schema-driven способом.

Reference attributes должны показывать human-readable object labels.

Array fields должны корректно отображаться.

Enum fields — canonical display labels.

============================================================
13. DEFAULT REPOSITORY QUERY
============================================================

При открытии Flow Manager default query:

scope = ENDPOINT_PAIR

Predicate:

(flow.source == endpointA &&
 flow.consumer == endpointB)

OR

(flow.source == endpointB &&
 flow.consumer == endpointA)

Поиск должен включать flows обоих направлений.

Нельзя выполнять прямой scan YAML из React component.

Запрос выполняется через Repo Core.

Предусмотреть API уровня domain/repository service, например:

searchIntegrationFlows({
    endpointA,
    endpointB,
    scope,
    text,
    filters,
    pagination
})

Названия адаптировать к существующей архитектуре.

============================================================
14. REPOSITORY INDEXING
============================================================

Если Repo Core уже имеет indexes/search service — использовать его.

Если отсутствует эффективный pair lookup, реализовать индекс на уровне Repo Core, а НЕ UI.

Conceptual pair key:

unorderedPair(A, B)

например:

PairKey(min(A,B), max(A,B))

Index:

PairKey -> IntegrationFlow refs

При repository mutations индекс должен обновляться.

Не перечитывать и не парсить весь YAML repository при каждом изменении search string.

============================================================
15. SEARCH
============================================================

Search работает минимум по:

- canonical/display ID;
- display name;
- description;
- source name/id;
- consumer name/id;
- data objects;
- technologies;
- status;

но конкретные searchable attributes должны уважать metamodel/search configuration.

Debounce text input.

Esc очищает search, если search имеет focus.

Search results должны сохранять membership state.

============================================================
16. EXTENDED SEARCH
============================================================

Требуется checkbox:

[ ] Искать во всем репозитории

Default:

false.

FALSE:

ищем только flows между A и B.

TRUE:

ищем все Integration Flows в Repository.

При TRUE table дополнительно показывает Source и Consumer для flows, не относящихся к текущей паре.

Current-pair flows должны визуально отличаться:

badge:

"Между текущими системами"

или equivalent.

Результаты current pair рекомендуется rank/sort выше остальных при равной search relevance.

============================================================
17. CRITICAL RULE ДЛЯ EXTENDED SEARCH
============================================================

Flow C -> D нельзя включить в Bundle A-B.

Для non-eligible flow:

membership checkbox = disabled.

Tooltip/accessibility description:

"Нельзя включить в этот жгут: поток связывает C → D"

Остаются доступны:

- просмотр;
- редактирование;
- клонирование.

Особенно важное действие:

"Клонировать для A ↔ B"

см. раздел Clone.

18. EMPTY STATES
============================================================

CASE 1:

Между A и B flows отсутствуют.

Показывать:

"Между System A и System B интеграционных потоков в репозитории нет."

Actions:

+ Создать поток

[ ] Искать во всем репозитории

CASE 2:

Search ничего не нашел:

"По заданным условиям потоки не найдены."

CASE 3:

Repository unavailable:

отдельный error state.

Не путать empty repository result с connection/query error.

============================================================
19. CREATE INTEGRATION FLOW
============================================================

Action:

+ Новый поток

Открывает Flow Editor внутри Flow Manager.

Не использовать tiny modal для большой metamodel-driven формы.

Так как create вызван из Bundle A-B:

Source и Consumer предварительно определены A и B.

В верхней части editor:

Направление:

(A -> B)
(B -> A)

Default направление можно определить:

bundle source node -> bundle target node

но пользователь должен явно видеть и иметь возможность переключить его.

При переключении:

Source и Consumer меняются местами.

- reference;
- array;
- validation;
- editor;

- description;
- source;
- consumer;
- endpoint;
- data objects;
- agreement;
- comments;
- technologies;
- technical use;
- async;
- protected;
- status;
- changes;

НО эти поля не являются основанием hardcode'ить KA v2023 format.

Frade должен работать с configurable metamodel.

============================================================
22. ADD CREATED FLOW TO BUNDLE
============================================================

В create form:

[x] Добавить в текущий жгут

Default = true.

После successful repository create:

1. получить canonical RepoObjectRef;
2. если checkbox enabled:
   добавить ref в Bundle через diagram command.

Если Repository create succeeded,
но membership update failed:

НЕ удалять автоматически только что созданный repository object.

Показать:

"Поток создан, но не удалось добавить его в текущий жгут."

Action:

"Повторить добавление"

Operation должен быть idempotent.

============================================================
23. EDIT INTEGRATION FLOW
============================================================

Edit изменяет canonical repository object.

Это НЕ diagram-only edit.

Все diagrams, которые ссылаются на данный flow, впоследствии должны видеть обновленные attributes.

Использовать Repository Mutation API.

Никакого direct file write из diagram package.

Form снова schema-driven.

============================================================
24. GLOBAL IMPACT OF EDIT
============================================================

UI должен явно различать:

"Исключить из жгута"

и

"Редактировать поток".

Редактирование меняет global repository object.

В editor показать ненавязчивый message:

"Изменения будут сохранены в цифровом репозитории и будут видны во всех представлениях этого потока."

Не показывать warning dialog для каждого обычного attribute edit.

Но endpoint changes имеют отдельное правило.

============================================================
25. EDIT SOURCE / CONSUMER
============================================================

Пользователь может редактировать attributes, включая Source и Consumer, если repository permissions это позволяют.

Если после edit flow по-прежнему связывает A и B:

membership остается.

Например:

A -> B

reverse:

B -> A

=> membership valid.

Если flow становится:

A -> C

и он входил в Bundle A-B:

перед Save показать inline/high-impact warning:

"После изменения поток больше не будет связывать System A и System B и будет исключен из текущего жгута."

Require explicit confirmation.

После successful Repository save:

remove flow from current Bundle through Diagram command.

Не удалять сам Integration Flow.

============================================================
26. OTHER DIAGRAMS AFTER ENDPOINT EDIT
============================================================

Не выполнять неявные массовые изменения закрытых diagrams.

Если endpoint change делает existing membership другого diagram Bundle invalid:

при следующей загрузке/валидации такого diagram должна обнаруживаться invalid membership.

Если в Frade существует Diagram Index / usage index:

можно показать impact count:

"Поток используется в N диаграммах."

Но implementation не должна становиться зависимой от наличия такого index.

============================================================
27. REVERSE DIRECTION
============================================================

Action:

"Поменять направление"

Semantics:

old.source -> new.consumer
old.consumer -> new.source

Все остальные attributes сохраняются.

Рекомендуемый UX:

action открывает Edit Flow state и сразу swaps Source/Consumer в draft.

Пользователь видит:

A -> B
становится
B -> A

Repository не изменяется до Save.

После Save:

- Repository object update;
- membership текущего Bundle сохраняется;
- canonical object ID сохраняется;
- flow НЕ клонируется;
- никакого delete/create.

Reverse должен быть pure transformation с unit tests.

============================================================
28. CLONE
============================================================

Clone создает НОВЫЙ Integration Flow object.

Новый object получает новый repository identity.

Копируются domain attributes, кроме:

- object ID;
- revision/version metadata;
- timestamps/audit fields;
- generated technical fields;
- fields, помеченных в schema как non-cloneable.

Clone policy должна быть centralized/domain-driven.

============================================================
29. CLONE ELIGIBLE FLOW
============================================================

Если original flow:

A -> B
или
B -> A

и текущий Bundle A-B:

Clone открывает Create Form:

- attributes copied;
- source/consumer preserved;
- new ID;
- "Добавить в текущий жгут" = true.

============================================================
30. CLONE FROM EXTENDED SEARCH
============================================================

Если найден:

C -> D

в Flow Manager A-B:

primary clone action:

"Клонировать для A ↔ B"

Открывает Create Form:

- business/technical attributes скопированы;
- source/consumer заменены current endpoints A/B;
- пользователь выбирает direction:
    A -> B
    B -> A;
- new ID;
- Add to current Bundle = true.

Дополнительно, если UX проекта это допускает:

"Клонировать как есть"

создает C -> D и не может автоматически добавить его в A-B.

Primary path в контексте Bundle — Clone for current Bundle.

============================================================
31. DELETE НЕ ВХОДИТ В SCOPE
============================================================

Данная задача НЕ реализует удаление Integration Flow из Repository.

"Исключить из жгута" != "Удалить".

Если delete functionality уже существует в global object editor, не переносить ее автоматически в Flow Manager.

============================================================
32. BROKEN REFERENCES
============================================================

Diagram может содержать RepoObjectRef, который больше не разрешается Repository.

Например object был удален внешним Git commit.

Flow Manager должен показывать:

"Недоступный поток"

с object ID/ref.

Status:

Broken reference.

Action:

"Исключить из жгута"

должно работать.

UI не должен падать.

Diagram validation должна фиксировать broken reference.

============================================================
33. REPOSITORY EVENTS / REFRESH
============================================================

Если Repo Core имеет event model, реагировать на:

ObjectCreated
ObjectUpdated
ObjectDeleted
RepositoryReloaded
RepositoryChanged

или соответствующие существующие events.

Flow Manager должен обновлять query/cache.

Если object update меняет eligibility:

recompute row eligibility.

Не плодить собственную event infrastructure, если она уже существует.

============================================================
34. READ-ONLY REPOSITORY
============================================================

Если Repository read-only, но Diagram writable:

разрешить:

- просматривать flows;
- search/filter;
- добавлять existing eligible refs в Bundle;
- исключать refs из Bundle.

Запретить:

- Create;
- Edit;
- Reverse;
- Clone.

Disabled controls должны объяснять причину.

============================================================
35. READ-ONLY DIAGRAM
============================================================

Если Diagram read-only:

membership checkbox disabled.

Но при writable Repository могут быть доступны global View/Edit операции согласно permission model приложения.

Использовать существующий permission model.

============================================================
36. REPOSITORY DISCONNECTED
============================================================

Connected-repository mode является основным scope.

Но Flow Manager не должен crash в disconnected mode.

Если repository connection отсутствует:

- показать понятное состояние;
- показать известные bundle refs, если diagram format содержит refs;
- repository search/create/edit disabled.

Не внедрять в рамках этой задачи полноценную offline snapshot model, если ее еще нет.

============================================================
37. RECONNECTING BUNDLE ENDPOINT
============================================================

Учесть изменение endpoint самого Diagram Bundle.

Пример:

Bundle A-B содержит:

F1 A -> B
F2 B -> A

Пользователь reconnect edge:

A-B
->
A-C

Перед завершением операции определить incompatible memberships.

Если существуют incompatible flows:

показать confirmation:

"При изменении конца жгута 2 потока перестанут соответствовать его системам и будут исключены из этого представления."

Continue:

- reconnect Bundle;
- удалить incompatible refs;
- сохранить eligible refs, если такие есть;
- всё сделать одной logical undoable operation.

Cancel:

- оставить старый endpoint;
- memberships unchanged.

Undo:

полностью восстановить old endpoint + refs.

41. PERFORMANCE
============================================================

Нельзя зависеть линейно от полного YAML repository на каждый render.

Требования:

- cancellation/stale query protection;
- pagination или virtualization для больших result sets;
- stable row keys = canonical RepoObjectRef;
- no N+1 repository lookups per row;
- reference display labels получать batch/bulk способом или через existing cache.

Reference performance fixture:

100 000 Integration Flows.

Flow Manager не должен пытаться materialize/render все строки одновременно.

Pair query должен использовать Repo Core index/query capability.

Actions:

- загрузить актуальную версию;
- повторить изменения;
- использовать существующий conflict resolution mechanism Frade.

Не создавать второй conflict framework.

65. DEFINITION OF DONE
============================================================

Change считается завершенной только если:

1. Bundle может существовать пустым.

2. Flow Manager показывает все Integration Flows между его endpoint systems/subsystems.

3. Оба направления A->B и B->A поддерживаются.

4. Пользователь может включить существующий flow.

5. Пользователь может исключить flow только из данной Diagram.

6. Repository flow при исключении не удаляется.

7. Пользователь видит все attributes flow.

8. Работает поиск.

9. Работают filters.

10. Работает checkbox "Искать во всем репозитории".

11. Flow из другой пары нельзя ошибочно включить в Bundle.

12. Можно создать новый flow.

13. Новый flow сохраняется через Repo Core.

14. Новый flow можно автоматически добавить в Bundle.

15. Можно отредактировать canonical flow.

16. Можно поменять direction source <-> consumer.

17. Reverse не меняет object identity.

18. Можно клонировать flow.

19. Clone имеет новую identity.

20. Clone from full-repository search может быть адаптирован к A-B.

21. Membership поддерживает Undo/Redo.

22. Reconnect Bundle корректно валидирует memberships.

23. Broken references не ломают Diagram.

24. UI не зависит от YAML.

25. Feature metamodel-driven.

26. Feature repository-adapter independent.

27. Existing diagrams backward compatible.

28. BDD scenarios реализованы.

29. Unit/component/E2E tests проходят.

30. OpenSpec validation проходит.
